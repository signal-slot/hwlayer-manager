## Summary of differences TDX vs ML v6.12

- **ML v6.12 has no AM62P support in tidss.** `D`tidss_drv.c at ML lists `ti,am625-dss` and the other pre-AM62P compatibles only; there is no `dispc_am62p51_feats`/`dispc_am62p52_feats`, no AM62P DSS node in `DTS`k3-am62p-main.dtsi, and no `k3-am62p5-verdin-*` device trees in `DTS` (src, ML: `git grep` over those paths returns nothing).
- **TDX adds** the two AM62P feature tables and compatibles, a DSS **shared mode** (remote core owns a video port and/or planes, Linux owns the rest), `max-memory-bandwidth` checking (also present in ML `tidss_dispc.c` :1278), a plane-underflow IRQ report, and dropped the mainline `get_scanout_buffer` helper for the primary plane.
- **Same in both** (a `git diff` of `tidss_plane.c` and `tidss_kms.c` shows only the points listed above): the plane check, scaling code, format table, blend-mode and alpha properties, zpos creation, `normalize_zpos`, the GO-bit use.

## What this means for the repository (inferred, not asserted by the source)

- **inferred**: the engine's two-plane composition (application plane beneath a safety plane) matches the hardware: two planes per DSS instance, ordered by an overlay manager, per-plane global alpha and pre-multiplied blending. The `backends/twoplane` memory-to-hardware table is not read here.
- **inferred**: under Linux with one output, the primary plane is the **lite** plane (cannot scale) and the overlay is the full VID plane. A Linux DRM user wanting to scale must put the scaled content on the overlay plane.
- **inferred**: with an R5F owning a video port in shared mode, Linux tidss sees only the planes and ports listed in the shared-mode properties; this is the mechanism the SK overlay shows for the "R5F safety plane under Linux content" layout. Whether Toradex's Verdin images ship an equivalent overlay or the firmware it names: not read.
- **To confirm on a board** (each needs the board's kernel and DT): `uname -r` against 6.6.163; which DSS node is enabled; the plane list, types, `zpos` ranges and `IN_FORMATS` through `drm_info`; a `TEST_ONLY` overlay-only commit; a `TEST_ONLY` scaled lite plane; and the two blend modes.

## Not covered

DSI/OLDI bridge behaviour, the `tidss_oldi.c` body, panel timings, the 6.18 branch, TI's SDK 'shared mode' firmware, and any register-level hardware behaviour beyond what the driver writes.
