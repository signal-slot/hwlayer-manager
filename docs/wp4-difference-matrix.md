# WP4 draft: AM62P vs i.MX95 difference matrix

> SoW.md §8 WP4: "Contrast the AM62P pipeline with i.MX95 and document which constraints are truly generic."

> **Two matrices, one scope (WP4).** This file is the compact, one-table form of the matrix: each cell carries its own tag and date, and the i.MX95 column includes the read-only observations of 2026-11-27 and 2026-11-28. [`am62p-imx95-matrix.md`](am62p-imx95-matrix.md) is the longer, sectioned form (Linux DRM side, MCU / Zephyr side, `backends/twoplane` per SoC, lease and Weston coexistence) and was written from the documents before those observations were merged. Read both; see "Known differences between the two matrices" at the end of this file where they disagree.

Draft written 2026-11-28 from documents already merged in this repository. It adds no finding, uses no device and read no document outside the repository. Nothing here is a claim toward M1, M2 or M3, and no cell is taken from one SoC to fill the other.

## Tags and sources

Every cell that is not `unknown` names the file it comes from and one tag, carried over from that file:

- **observed (date)**: seen on a board; the date is the source's own. All observed cells below are i.MX95 and on Linux (`probe` capture 2026-11-28, kernel 6.6.157-7.8.0; read-only ssh snapshot 2026-11-27). **No AM62P cell is observed**.
- **read from source**: stated by driver, firmware or tool source, or by `SoW.md` (a description of the existing AM62P demo, not checked by this repository). Not run.
- **inferred**: concluded by the named document from what it read or observed; it does not state it itself.
- **unknown**: no merged document in the list says it. This is not "no" and not "absent".

Files used: `docs/platform-capabilities.md`, `docs/twoplane-backend.md`, `docs/imx95-zephyr-feasibility.md`, `docs/imx95-m7-fb-memory.md`, `docs/imx95-m7-dpu-irq.md`, `docs/imx95-twoplane-port.md` and `SoW.md`. `docs/platform-capabilities.md` says of the AM62P only "Not researched yet". The AM62P column therefore rests on `SoW.md` (§5.2, §7) and `docs/twoplane-backend.md`.

## What the matrix does and does not support

- **Compared with certainty**: only what both columns hold at the same tag. Today that is the shape of the engine's driver contract (a per-frame callback, a commit count and a latched count; `docs/twoplane-backend.md`, read from source) and the SoW's cache and trust-boundary requirement (`SoW.md` §7). No hardware value is observed on both sides.
- **Which constraints are truly generic** (the WP4 question): not answerable yet. The AM62P column is `unknown` for the Linux side and for ownership, firmware and format limits, and no AM62P cell is observed (`docs/platform-capabilities.md`: "Not researched yet").
- **Hardware-specific on the i.MX95 side**, as the sources record it: shared scaler and fetch-unit pool, upscale only, 2048 scaled source limit, no rotation, owner decided by the System Manager config (`docs/platform-capabilities.md`, `docs/imx95-zephyr-feasibility.md`). Whether any of these has an AM62P counterpart: unknown.

## Gaps for the planner (not done here)

1. AM62P: Linux DRM driver, plane list, formats, scaling, blending, z-order, TI firmware and resource assignment, interrupt ownership. The demo's own docs and sources, named in `SoW.md` §5.2, are not read here. Issue #12 (AM62P board work) is not touched.
2. i.MX95: the board's SM config (and whether the Linux side may start the M7) is still open in `docs/imx95-zephyr-feasibility.md`; the M7 rows will change once it is read.
3. Any observed value on the AM62P, and any Zephyr-side measurement on the i.MX95.
4. `docs/am62p-imx95-matrix.md` already holds an earlier comparison with its own tag scheme; the two documents overlap. They are now cross-linked and their differences are listed under "Known differences between the two matrices"; only merging them into one remains open.
