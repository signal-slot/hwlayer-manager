# Continuous integration

`.github/workflows/ci.yml` (workflow `ci`, job `checks`) runs on every pull request to `main` and every push to `main`, on `ubuntu-latest`, with the latest stable Rust and the committed `Cargo.lock`. It runs `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and `cargo test --workspace`, which also compiles and runs the C tests with the runner's `cc` (among them the AM62P board test's scene sequence behind a fake panel, `tests/board/am62p_r5f/`) and checks the freestanding backend object with `nm`. The board test's firmware itself is not built in CI. It then builds `composition-core` for `thumbv7em-none-eabihf`, and builds the static library for the same target without `std`, with `panic-handler`, in release. Last, it cross-builds for aarch64 Linux with `scripts/cross-aarch64.sh --locked` (target `aarch64-unknown-linux-musl`, static, linked by `rust-lld`, so no aarch64 gcc is needed; if the runner's Rust cannot provide the target, the script falls back to a private rustup in a cache directory, see `scripts/cross-aarch64-README.md`; the cache is `${HWLAYER_XBUILD_CACHE:-${XDG_CACHE_HOME:-$HOME/.cache}/hwlayer-manager/xbuild}`, a few hundred MB, cleared by removing that directory): the `composition-drm` library, its `probe` example, and the `drm-harness` binary of `composition-drm-harness` (`tools/drm-harness`, built with `-p composition-drm-harness --bin drm-harness`). The documented recipe for these tools is `scripts/cross-aarch64.sh` with no arguments (probe and harness), or the three explicit lines of the CI step; a bare `cargo build --locked` for the probe is not the recipe. This step only compiles and links; it runs nothing, on the runner or on a board, so it shows that the Linux i.MX95 builds compile, not that they work. It does not run the vkms tests: they stay ignored, and `scripts/vkms-vm-test.sh`, which boots a kernel in QEMU, is not part of CI. It builds and runs nothing on a board, does not compile the C backend for Arm (the `arm-backend` job below does). The minimum Rust version is tested by the `msrv` job below, not by this job. Hardware milestones are never claimed from it. A green run means the host tests and the bare-metal Rust builds pass, and says nothing about hardware.

## Job `arm-backend`

A second job of the same workflow, on `ubuntu-latest`, installs `clang`, `lld` and `llvm` (apt) and the Rust targets `thumbv7em-none-eabihf` and `armv7r-none-eabihf`, and runs `CC_KIND=clang scripts/check-arm-link.sh`. For each of Cortex-M7 (`-mcpu=cortex-m7 -mfpu=fpv5-d16 -mfloat-abi=hard -mthumb`) and Cortex-R5 (`-mcpu=cortex-r5 -mfloat-abi=hard`) the script:

1. compiles `backends/twoplane/ce_twoplane.c` with `-ffreestanding -O2 -Wall -Wextra -Werror`;
2. builds `composition-ffi-staticlib` for the Rust target (`--no-default-features --features panic-handler`, release), which holds the engine symbols the backend calls;
3. links the backend object, the start-up and a stub `main` (`backends/twoplane/arm/start.c`, `main.c`; stub driver and port, nothing real) and that library into a freestanding image with `-nostdlib`, the linker script of `backends/twoplane/arm/` (`cortex-m7.ld`, `cortex-r5.ld`: a FLASH and a RAM region at addresses of no board) and no runtime library other than the engine's;
4. runs `nm` on the image and fails if any symbol is undefined, or if a symbol the backend object calls is not defined in the image (`__aeabi_memclr4` for clang, `memset` for GCC).

Where `__aeabi_memclr4` comes from: with clang the backend object needs it (the compiler emits it to clear structures); Arm GCC 14.2.1 emits a call to `memset` instead, which the same library defines, and then `__aeabi_memclr4` is not required. The engine static library carries Rust's `compiler_builtins`, which defines it (weak), so that is the definition the image gets (with GCC, `-lgcc` comes after the library as a fallback); the linker map (`target/arm-link/<cpu>/image.map`, printed by the script) shows the input. Firmware that does not link the Rust library must take the symbol from its own runtime (newlib, compiler-rt or its own).

What it proves: the backend compiles warning-free for both cores with clang, and the engine library and the backend link together with every symbol resolved. What it does not prove: anything about running. Nothing is run, on an MCU, a board or an emulator; the image has no clocks, interrupts or real driver. It is not a board result, and it does not replace the M3 board run. `scripts/check-arm-link.sh` also works locally; with `CC_KIND=gcc` (or when `arm-none-eabi-gcc` is on PATH) it uses Arm GCC and `-lgcc` instead. Run locally on 2026-11-28 with clang and `rust-lld`: both images link, `__aeabi_memclr4` is defined from `compiler_builtins`, and no symbol is undefined. Also run locally on 2026-11-28 with the xPack build of Arm GCC 14.2.1 (arm-none-eabi-gcc 14.2.1-1.1) for both cores: both images link, `memset` is defined, no symbol is undefined (ld warns about a missing .note.GNU-stack section).

## Job `msrv`

The workflow `ci` has a job `msrv` (read from source, `.github/workflows/ci.yml`, 2026-11-28). It installs exactly Rust 1.83.0 with the minimal profile and the `thumbv7em-none-eabihf` target, the floor measured in `docs/msrv.md` (observed, 2026-11-28, see that file). It runs `cargo build --workspace --locked`, `cargo test --workspace --locked`, `cargo build -p composition-core --target thumbv7em-none-eabihf --locked`, and the static-library build (`-p composition-ffi-staticlib --no-default-features --features panic-handler --target thumbv7em-none-eabihf --release --locked`). It does not run clippy or rustfmt. The job was added on 2026-11-28 and has not yet run on a pull request (observed, 2026-11-28); nothing here claims it passes. The version in the job must be kept equal to `rust-version` in `Cargo.toml` (inferred: otherwise the job tests a different floor than the declared one).
