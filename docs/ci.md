# Continuous integration

`.github/workflows/ci.yml` (workflow `ci`, job `checks`) runs on every pull request to `main` and every push to `main`, on `ubuntu-latest`, with the latest stable Rust and the committed `Cargo.lock`. It runs `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and `cargo test --workspace`, which also compiles and runs the C tests with the runner's `cc` and checks the freestanding backend object with `nm`. It then builds `composition-core` for `thumbv7em-none-eabihf`, and builds the static library for the same target without `std`, with `panic-handler`, in release. Last, it cross-builds for aarch64 Linux with `scripts/cross-aarch64.sh --locked` (target `aarch64-unknown-linux-musl`, static, linked by `rust-lld`, so no aarch64 gcc is needed): the `composition-drm` library, its `probe` example, and the `drm-harness` binary of `composition-drm-harness` (`tools/drm-harness`). This step only compiles and links; it runs nothing, on the runner or on a board, so it shows that the Linux i.MX95 builds compile, not that they work. It does not run the vkms tests: they stay ignored, and `scripts/vkms-vm-test.sh`, which boots a kernel in QEMU, is not part of CI. It builds and runs nothing on a board, does not compile the C backend for Arm (the `arm-backend` job below does), and does not test the minimum Rust version (the `rust-version` of `Cargo.toml`). Hardware milestones are never claimed from it. A green run means the host tests and the bare-metal Rust builds pass, and says nothing about hardware.

## Job `arm-backend`

A second job of the same workflow, on `ubuntu-latest`, installs `gcc-arm-none-eabi` (apt) and the Rust targets `thumbv7em-none-eabihf` and `armv7r-none-eabihf`, and runs `CC_KIND=gcc scripts/check-arm-link.sh`. For each of Cortex-M7 (`-mcpu=cortex-m7 -mfpu=fpv5-d16 -mfloat-abi=hard -mthumb`) and Cortex-R5 (`-mcpu=cortex-r5 -mfloat-abi=hard`) the script:

1. compiles `backends/twoplane/ce_twoplane.c` with `-ffreestanding -O2 -Wall -Wextra -Werror`;
2. builds `composition-ffi-staticlib` for the Rust target (`--no-default-features --features panic-handler`, release), which holds the engine symbols the backend calls;
3. links the backend object, the start-up and a stub `main` (`backends/twoplane/arm/start.c`, `main.c`; stub driver and port, nothing real) and that library into a freestanding image with `-nostdlib`, the linker script of `backends/twoplane/arm/` (`cortex-m7.ld`, `cortex-r5.ld`: a FLASH and a RAM region at addresses of no board) and `-lgcc` last;
4. runs `nm` on the image and fails if `__aeabi_memclr4` is not defined or if any symbol is undefined.

Where `__aeabi_memclr4` comes from: the backend object needs it (the compiler emits it to clear structures). The engine static library carries Rust's `compiler_builtins`, which defines it (weak), and it comes before `-lgcc` on the link line, so that is the definition the image gets; the linker map (`target/arm-link/<cpu>/image.map`, printed by the script) shows the input. libgcc's `-lgcc` stays on the line as the fallback runtime library. Firmware that does not link the Rust library must take the symbol from its own runtime (newlib, compiler-rt or its own).

What it proves: the backend compiles warning-free for both cores with Arm GCC, and the engine library and the backend link together with every symbol resolved. What it does not prove: anything about running. Nothing is run, on an MCU, a board or an emulator; the image has no clocks, interrupts or real driver. It is not a board result, and it does not replace the M3 board run. `scripts/check-arm-link.sh` also works locally; without `arm-none-eabi-gcc` it uses clang with `ld.lld` or the Rust toolchain's `rust-lld` (`CC_KIND=clang`). Run locally on 2026-11-28 with clang 23 and `rust-lld` (`CC_KIND=clang`): both images link, `__aeabi_memclr4` is defined from `compiler_builtins`, and no symbol is undefined. The GCC path that the job uses was not run locally (no Arm GCC on that machine).
