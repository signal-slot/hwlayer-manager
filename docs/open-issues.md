## M2: i.MX95 Zephyr (SoW §5.1, WP3, §9 M2)

State: **M2 is not passed, and this repository has no board result for it.** What exists is source reading, one read-only board snapshot, host builds and a QEMU run. Each item below carries its tag. "Feasibility" is `docs/imx95-zephyr-feasibility.md`.

- **Observed (2026-11-27), read-only:** `docs/imx95-zephyr/` (`observed-2026-11-27.txt`) is an ssh snapshot of the Verdin iMX95 (Reference Multimedia Image 7.8.0, kernel 6.6.157-7.8.0). It shows `remoteproc1` (`imx-rproc`) `offline` with firmware name `rproc-imx-rproc-fw`; the DPU, LDB channel 0 and pixel link held by Linux with the display power domain on; DSI `disabled`; SCMI v2.1, vendor `NXP:IMX`, firmware version 0x23e. It does not show which System Manager configuration the board runs.
- **Read from source and inferred:** Feasibility is the ownership analysis. Under NXP's `mx95evk` configuration the Linux logical machine holds every display resource and the M7 logical machine none (read from source). Giving the display to the M7 needs an SM configuration rebuild, a new boot container and a Linux DT change, which the board rules forbid (Feasibility §4, B4). Its gate for starting an M7 image through remoteproc is **not met** (Feasibility §8). Supporting source studies, all desk research with no board access: `docs/imx95-sm-display-lm.md` (an inferred SM configuration, and why it cannot be applied here), `docs/imx95-display-handover.md`, `docs/imx95-display-power.md`, `docs/imx95-display-clocks.md`, `docs/imx95-verdin-bsp-src.md`, `docs/imx95-m7-rproc-load.md`, `docs/imx95-m7-scmi.md`, `docs/imx95-m7-dpu-driver.md`, `docs/imx95-m7-dpu-irq.md`, `docs/imx95-m7-lvds-route.md`, `docs/imx95-m7-verdin-bsp.md`, `docs/imx95-m7-console.md`, `docs/imx95-verdin-zephyr-board.md`, `docs/imx95-m7-fb-memory.md`.
- **System Manager ownership, state 2026-11-28:**
  - *Read from source, 2026-11-28:* Toradex builds its own fork `imx-sm-toradex` with `SYSTEM_MANAGER_CONFIG = "verdin-imx95"`, and its `configs/verdin-imx95.cfg` could not be fetched, so it is unread (`docs/imx95-verdin-sm-config.md` §1, §2). The Verdin container is built with `flash_a55`, which carries no M7 image.
  - *Read from source, 2026-11-28, NXP `mx95evk.cfg` at `lf-6.6.52-2.2.2`:* the logical machine "AP" (LM2, the AP-NS agent, Linux) owns the DPU `DC` and its sub-blocks, `LVDS`, `MIPI_DSI`, `BLK_CTRL_DISPLAYMIX`, `VIDEO_PLL1` and the pixel and LDB PLL clock permissions. The M7 logical machine (LM1) holds none of them. The display bus clocks DISPAPB, DISPAXI and DISPOCRAM belong to the SM's own LM0 (`docs/imx95-verdin-sm-config.md` §3, §4; `docs/imx95-sm-display-lm.md`).
  - *Inferred for Verdin, 2026-11-28:* the same split holds on the Verdin, because only the NXP file was read. A Toradex edit to the display or M7 sections would change it. Under it, the display cannot be shared between Linux and the M7 side by side, and neither AP agent holds `CPU_M7P` (`docs/imx95-verdin-sm-config.md` §5).
  - *Observed, 2026-11-28 (`docs/imx95-zephyr/observed-2026-11-28.txt`, read-only):* the DPU node's `clocks` list holds the SCMI clock IDs 80 (pix), 75 (apb), 76 (axi), 78 (ocram) and 37 (ldb_vco), and its `power-domains` is 13 (display). They match the IDs read from source in `docs/imx95-dpu-scmi-ids.md`.
  - *Observed, 2026-11-27 (`docs/imx95-zephyr/observed-2026-11-27.txt`, `clk_summary`):* `dispaxi` reads 800000000 Hz, enable count 2, consumer the display controller. Linux's DT asks for 400 MHz for DISPAXI (read from source), so the two differ; the cause is not known. The same snapshot shows `ldbpll_vco` at 2986200000 Hz and `ldb_pll_div7` at 71100000 Hz.
  - *Open, 2026-11-28:* whether the AP-S or AP-NS agent holds rights on `CPU_M7P` in the Verdin configuration. The NXP `mx95evk` file gives neither agent a `CPU_M7P` line, while `mx95evkrpmsg.cfg` gives both agents rights over the M7 and `LMM_1` (read from source). This is also check (c) of the remoteproc gate (M2-08).
