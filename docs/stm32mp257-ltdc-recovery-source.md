| FIFO underrun error (`ISR_FUEIF`) | `ldev->fifo_err++` | with `caps.fifo_threshold` (MP25): `DRM_WARN("ltdc fifo underrun: please verify display mode\n")` on any non-zero `fifo_err`, then the counter is set to 0 | read from source: `ltdc.c:1030-1031`, message `2030-2034` |
| FIFO underrun warning (`ISR_FUWIF`) | `ldev->fifo_warn++` | counted, but **on MP25 never turned into a message**: the warn counter is compared with the threshold only in the `else` branch, taken when `caps.fifo_threshold` is false. | FIFO underrun in rotation (`ISR_FURIF`) | `ldev->fifo_rot++` | `DRM_WARN("ltdc fifo rotation error\n")`, then the counter is set to 0 | read from source: `ltdc.c:1034-1035`, message `2025-2028` |
| Register reload error | none (section 1) | none | read from source |
| CRC error flag | none (section 1) | none | read from source |

If no plane is updated after an underrun, no message appears until one is | `ltdc.c:2017-2041` (end of `ltdc_plane_update`) | read from source |

## 4. Does the driver recover by itself?

| Claim | Where | Tag |
| --- | --- | --- |
| After a FIFO underrun, transfer error or rotation underrun the driver only counts and, at the next plane update, warns. It does not stop the CRTC, reset the controller, clear a layer, change the threshold or schedule a modeset | `ltdc_irq_thread` (`1005-1039`) and the warn block (`2019-2041`) contain no such call | read from source |
| The underrun threshold is a constant (`FUT_DFT`), not adapted after an error | `ltdc.c:267`, `1274-1276`, `2745` | read from source |
| The controller's own behaviour after an underrun (it keeps scanning out, with a corrupted line or frame, until the FIFO refills) is the reference manual's, not the driver's | not in `ltdc.c` | inferred (the source gives no handling) |
| The only reset of the LTDC block is at probe, and only when `GCR_LTDCEN` is clear: `reset_control_assert` then `deassert`. A running controller is never reset there, to keep a boot splash continuous | `ltdc.c:2718-2729` (`ltdc_load`) | read from source |
| Clock and PM errors at enable are **silent to user space**: `ltdc_crtc_atomic_enable` is a `void` helper. On a `clk_set_parent` or `clk_set_rate` failure or a failed `pm_runtime_resume_and_get` it prints `DRM_ERROR("Could not set parent clock: %d\n")`, `DRM_ERROR("Cannot set rate (%dHz) for pixel clk\n")` or `DRM_ERROR("Failed to enable crtc, cannot resume pm\n")` and **returns without enabling the controller**, while the atomic commit that called it still returns 0 and the CRTC state says active | `ltdc.c:1118-1134`, `1166-1169` (`ltdc_crtc_atomic_enable`); the commit result follows from a `void` helper | read from source (the messages and early returns); inferred (that the ioctl reports success) |
| The same applies to the disable path: a `clk_set_parent` failure returns early before the vblank event flush at the end of `ltdc_crtc_atomic_disable` | `ltdc.c:1323-1328` against `1338-1344` | read from source |
| `ltdc_crtc_enable_vblank` returns `-EPERM` if the CRTC state is not enabled, so a vblank reference cannot be taken on a disabled CRTC | `ltdc.c:1447-1458` | read from source |
| Mode validity: `ltdc_encoder_mode_valid` rejects a mode whose pixel clock the clock tree cannot round to within `clock_tolerance` (`MODE_CLOCK_LOW`/`MODE_CLOCK_HIGH`) and any mode above `pad_max_freq_hz`, but accepts every `PREFERRED` mode inside the pad limit. A mode that is accepted but whose clock is off, or whose bandwidth does not fit the memory path, is where an underrun comes from; the driver does not check bandwidth | `ltdc.c:2320-2367` | read from source (the checks); inferred (the link to underrun) |

## 5. What a fresh atomic modeset does after an error

| Claim | Where | Tag |
| --- | --- | --- |
| The driver sets `mode_changed` whenever `active` changed, so any off-then-on is a full modeset: `ltdc_crtc_atomic_check` | `ltdc.c:1372-1384` | read from source |
| A modeset runs `ltdc_crtc_atomic_enable`, which, when the block is already powered (`pm_runtime_active`), first **disables all layers, commits that immediately** (`SRCR_IMR` or per-layer `LXRCR_IMR`) **and clears `GCR_LTDCEN`**; if it is not powered it resumes it. It then reprograms the timing registers, polarities, output converter and background colour, re-enables `IER_FUWIE\|IER_FUEIE\|IER_TERRIE`, rewrites the FIFO threshold and sets `GCR_LTDCEN` | `ltdc.c:1147-1170` (the power branch), `1190-1276` | read from source |
| So after an underrun, a modeset (including the same mode) clears the controller's scan-out state and restarts it. It does not clear the four counters on the enable side; they are cleared in `ltdc_crtc_atomic_disable` (`1330-1336`), which runs when the CRTC is turned off first | `ltdc.c:1282-1344` | read from source |
| `ltdc_crtc_atomic_disable` turns the vblank off (`drm_crtc_vblank_off`), disables every layer, clears the error enables, forces an immediate reload, clears `GCR_LTDCEN` (and `GCR_ROTEN`), selects the pinctrl sleep state, drops the runtime-PM reference with `pm_runtime_put_sync_suspend`, restores the pixel-clock parent and zeroes the counters | `ltdc.c:1282-1336` | read from source |
| A pending page-flip event on a CRTC that is being turned off is sent at the end of `ltdc_crtc_atomic_disable` (`drm_crtc_send_vblank_event`) when `crtc->state->event` is set and the CRTC is not active, so a commit that disables the CRTC still delivers its event | `ltdc.c:1338-1344` | read from source |
| `ltdc_crtc_atomic_flush` arms the commit's event on the next vblank (`drm_crtc_arm_vblank_event`) if a vblank reference can be taken, and otherwise sends it at once (`drm_crtc_send_vblank_event`). It requests the shadow reload (`SRCR_VBR`) first on hardware without per-layer shadow registers | `ltdc.c:1347-1370` | read from source |
| The plane path re-enables a layer only when `ldev->plane_enabled[]` is set, which `ltdc_plane_atomic_enable` sets and `ltdc_plane_atomic_disable` clears. After a CRTC off the helpers disable each plane, so the next modeset's commit must carry the planes again | `ltdc.c:2059-2105` | read from source |
| The DSI bridge chain is brought up by the DRM core's bridge helpers around this: `dw_mipi_dsi_bridge_atomic_pre_enable` runs the host's `mode_set` (PHY init), and `dw_mipi_dsi_bridge_atomic_enable` switches the host to video mode, in that order, with no error return (`void`). Disable: `post_atomic_disable` sets command mode, powers the PHY off and writes the `PWR_UP` and `PHY_RSTZ` resets | `dw-mipi-dsi.c`, functions `dw_mipi_dsi_bridge_atomic_pre_enable`, `dw_mipi_dsi_bridge_atomic_enable`, `dw_mipi_dsi_bridge_post_atomic_disable`, `dw_mipi_dsi_mode_set`, `dw_mipi_dsi_disable` | read from source (no line numbers, see "Sources") |
| The DSI host driver has **no interrupt handler** and no error log for host errors. `dw_mipi_dsi_clear_err` reads `DSI_INT_ST0` and `DSI_INT_ST1`, discards them and writes 0 to the two mask registers; it is called once, from `dw_mipi_dsi_mode_set`. PHY lock and clock-lane stop timeouts in `dw_mipi_dsi_dphy_enable` are `DRM_DEBUG_DRIVER` lines only, **not errors, and do not abort**; `Phy init() failed`, `Phy get_lane_mbps() failed` and `Failed to set mode, cannot resume pm` are also debug-level, and `mode_set` continues after the first two | `dw-mipi-dsi.c`, functions `dw_mipi_dsi_clear_err`, `dw_mipi_dsi_dphy_enable`, `dw_mipi_dsi_mode_set` | read from source (no line numbers) |
| The DSI command path logs real errors: `failed to get available write payload FIFO`, `Timeout during read operation`, `Read payload FIFO is empty`, `failed to create packet: %d` (`dev_err`); the command-FIFO timeouts (`failed to get available command FIFO`, `failed to write command FIFO`) are `dev_dbg`. They return the error to the caller, with no flush, reset or retry. These belong to DSI commands to the peripheral, not to the video stream | `dw-mipi-dsi.c`, `dw_mipi_dsi_write`, `dw_mipi_dsi_read`, `dw_mipi_dsi_host_transfer`, `dw_mipi_dsi_gen_pkt_hdr_write` | read from source (no line numbers) |
| `dw_mipi_dsi_bridge_mode_valid` accepts every mode unless the platform glue supplies a `mode_valid`; whether `dw-mipi-dsi-stm.c` does (a PHY-rate check) is not known | `dw-mipi-dsi.c`, `dw_mipi_dsi_bridge_mode_valid`; `dw-mipi-dsi-stm.c` not read | read from source (the core); not read (the ST glue) |
| `dw-mipi-dsi-stm.c`: PLL lock, `phy_init` and `phy_power_on` failure handling | not read (HTTP 404 at this commit) | not read |
| LVDS (`lvds.c`) has no interrupt handler and no recovery code. A PLL lock timeout in `lvds_pll_enable` is `drm_err("!TIMEOUT! waiting PLL, let's continue\n")` and the sequence **continues**; the error is returned only through the clock `.enable` op (`lvds_pixel_clk_enable`, `Failed to enable primary/secondary PHY PLL: %d`). `lvds_atomic_enable` runs the whole sequence on each enable (regulators, runtime PM, mode and data mapping, `CR_LVDSEN`, panel prepare/enable); on its silent error paths it does not release the runtime-PM reference. | The ADV7535 bridge, the HDMI hot-plug and EDID paths that decide whether the connector goes `connected` again after a loss | not read | not read |

## 7. Mapping to A5, A6 and the trace-check counts

Scenarios: [`stm32mp257-board-scenarios.md`](stm32mp257-board-scenarios.md) and `scripts/board-scenarios.sh` (the header comment gives each row's PASS rule). The fake model: `crates/composition-fake/tests/stm32mp257_scenarios.rs` ("no hotplug, EDID or link-training behaviour"). The trace format and the `trace-check` counts: [`trace-format.md`](trace-format.md), `tools/drm-harness/src/trace.rs` (`Counts`), `scripts/board-scenarios.sh` (`check_trace`). `scripts/check-trace-log.sh` checks only a log's **header** (version, date and the host/not-a-hardware-result note), not counts.

| Point | A5 modeset | A6 recovery | trace-check | Tag |
| --- | --- | --- | --- | --- |
| A modeset is a full off/on of the controller (layers off, `LTDCEN` off, timing reprogrammed, `LTDCEN` on) | The mode switch (section 5) exercises exactly this path; the first commit after it carries the modeset and blocks. The driver gives no error for a clock that cannot be set, so a PASS means the page-flip event came, not that the new mode is on the wire | The new run's first commit is a modeset on a CRTC that was turned off: it is the "recovery" | `commit` counts successful ioctls (`commit_ok`), so a modeset commit counts as one | read from source (kernel); inferred (mapping) |
| Page-flip event after a modeset | `modeset-after` commits must each have `latency_us` (the runner's own check); the event is armed by `ltdc_crtc_atomic_flush` and arrives on the first line interrupt after enable | Same for `recovery-after`; the runner requires `latched == commits` for each of the two steps | `latched` counts the `latched` events; A5 and A6 compare it with the harness's own commits that have `latency_us` (`texpect latched`) | read from source (`board-scenarios.sh:229-235`, `ltdc.c:1347-1370`) |
| FIFO underrun or transfer error during the hold | **Not detected by any A5 check.** The row passes with an underrun, because KMS shows none (section 6). The picture hook, not the trace, is the only way to see its effect | Same | None of the counts: there is no trace event for it | read from source (rule text) ; inferred (consequence) |
