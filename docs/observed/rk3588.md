# RK3588 (Rockchip VOP2), observed on a FriendlyElec NanoPC-T6

Staging file for the per-SoC section of `docs/platform-capabilities.md`.
Everything tagged **observed 2026-11-27** was measured on the board on
2026-11-27 between 18:32 and 18:42 UTC. Rows tagged **inferred** are
conclusions drawn from those measurements; nothing here was read from kernel
source.

Tools: `probe` and `twoplane` examples of `composition-drm` at commit
`b0f3ef3`, cross-built on the host for `aarch64-unknown-linux-musl`, linked
with `rust-lld`, static (not with `scripts/cross-aarch64.sh`). Raw KMS
properties (possible_crtcs, full `IN_FORMATS`, property ranges and enums) were
read with a small read-only ioctl script outside the repository, because the
image has neither `modetest` nor `drm_info` and nothing was installed.

### Harness limitation and proposed change

`twoplane` insists on putting the background on a plane of kind `Primary`
with a linear 32-bit RGB format (`crates/composition-drm/examples/twoplane.rs`,
the `pick(PlaneKind::Primary, …)` check and the first-plan check
"the background is not on the primary plane"). On RK3588 the primary planes
(Cluster windows) are AFBC-only, and the kernel accepts an active CRTC without
its primary plane. The harness was **not** changed in this repository. For the
measurements below a local copy was built with this diff (kept out of the
repository):

```diff

+++ b/crates/composition-drm/examples/twoplane.rs

-    let Some(primary_format) = pick(
-        PlaneKind::Primary,
-        &[
-            PixelFormat::XRGB8888,
-            PixelFormat::ARGB8888,
-            PixelFormat::XBGR8888,
-            PixelFormat::ABGR8888,
-        ],
-    ) else {
+    let background_order = [
+        PixelFormat::XRGB8888,
+        PixelFormat::ARGB8888,
+        PixelFormat::XBGR8888,
+        PixelFormat::ABGR8888,
+    ];
+    let background_kind = if pick(PlaneKind::Primary, &background_order).is_some() {
+        PlaneKind::Primary

+        PlaneKind::Overlay
+    };
+    let Some(primary_format) = pick(background_kind, &background_order) else {
```

## What this suggests for a DriverProfile (not implemented)

All of this is inferred from the observations above; `profile.rs` was not
changed.

- **Linear buffers have four usable planes, none of them Primary.** Cluster
  windows (both primaries and Cluster2/3) list only AFBC modifiers, and the
  kernel runs VP0 with its primary off. A profile, or the generic planner,
  should not require the bottom layer to be on a Primary plane; on this
  driver a full-screen Esmart window at zpos 0 works.
- **Do not truncate silently.** Cluster planes list 126 format/modifier pairs;
  `MAX_FORMATS` = 32 keeps the first 32, which cuts most AFBC variants. A
  profile could keep one AFBC modifier per format, or the backend could say
  that it truncated.
- **Scaling exists but is not advertised.** `TEST_ONLY` accepted 2x up and 2x
  down on an Esmart window. A profile could claim scaling for Esmart (limits
  beyond 2x were not measured; Cluster scaling was not tested because no AFBC
  buffer was available).
- **Coverage blending with plane alpha < max is wrong on screen** while the
  kernel accepts it. A profile should prefer premultiplied buffers, or refuse
  coverage with a plane alpha below 0xffff.
- **zpos is shared and mutable 0..7**, and a swap works; the planner moved the
  layers to the other planes instead of rewriting zpos.
- **Rotation is per window type** (Cluster: 90/270 and both reflections;
  Esmart: reflect-y only). The backend maps none of it today.
- **Two exposed CRTCs share Cluster2/3 and Esmart0..3** (`possible_crtcs
  0b11`); with both ports active the two outputs would compete for them. Not
  tested: HDMI-A-2 had no display.

## Not measured

- A second active output (HDMI-A-2 disconnected), so no cross-CRTC sharing.
- AFBC buffers (dumb buffers are linear), so nothing on Cluster windows except
  fbcon's own framebuffer.
- YUV formats, scaling limits beyond 2x, and `modetest` output (not on the
  image).
