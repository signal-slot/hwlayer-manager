# BCM2712 (Raspberry Pi 5): probe and two-plane harness

Staging notes for the BCM2712 section of `docs/platform-capabilities.md`. Tags follow that file:
**observed** = measured on the board on the stated date, **inferred** = derived from observed
data, not measured directly. Nothing here is read from source. The raw KMS property dump of the
same board (rotation values, the full `IN_FORMATS` with modifiers, the plane masks of all four
CRTCs) is in `docs/observed/bcm2712-topology.md` (item probe-rpi5); this file adds the probe
and two-plane harness runs.

The session ran on 2026-11-28 JST; the board clock reported 2026-11-27 18:32-18:40 UTC, which
is the date the harness prints in its `DATE` line. Rows are tagged with the JST date.

None of this is a claim toward M1 to M3.

### Build

`probe` and `twoplane` from this repository at commit b0f3ef3, built on the host with
`cargo build --release -p composition-drm --example probe --example twoplane --target aarch64-unknown-linux-musl --config target.aarch64-unknown-linux-musl.linker="rust-lld"`
into a target directory outside the repository (static binaries, not `scripts/cross-aarch64.sh`).
Copied to `/tmp` on the board, run with `sudo`, removed afterwards. Nothing was installed on
the board.

## Harness findings (not fixed; proposed diffs)

1. **`--swap-z` cannot run on vc4.** The harness requires the background on the primary
   (`the background is not on the primary plane` is an error) and skips the swap if any planned
   plane has a fixed zpos. On vc4 the primary zpos is immutable, so the swap never runs, though
   two overlays (mutable 1..=17) could carry both layers. A proposed change, not built or tested:
   with `--swap-z`, if the primary of the output has a fixed zpos, hide the primaries from the
   caps the planner sees so both layers land on overlays, and accept a background on an overlay
   in that case.

   ```diff
   --- a/crates/composition-drm/examples/twoplane.rs
   +++ b/crates/composition-drm/examples/twoplane.rs
   @@ (where the first plan is checked)
   -            if assignments[0].layer != 0 || kind(0) != Some(PlaneKind::Primary) {
   +            let overlays_only = options.swap_z && primary_zpos_fixed;
   +            if assignments[0].layer != 0
   +                || (!overlays_only && kind(0) != Some(PlaneKind::Primary))
   +            {
                    errors.push("the background is not on the primary plane".into());
                }
   @@ (after the capabilities are probed, before the engine is built)
   +    // vc4 and others: the primary's zpos is immutable, so a swap needs two overlays.
   +    let primary_zpos_fixed = caps.planes.iter().any(|p| {
   +        p.kind == PlaneKind::Primary
   +            && p.outputs & (1 << options.output) != 0
   +            && matches!(p.zpos, Zpos::Fixed(_))
   +    });
   +    if options.swap_z && primary_zpos_fixed {
   +        for plane in caps.planes.iter_mut().filter(|p| p.kind == PlaneKind::Primary) {
   +            plane.outputs &= !(1 << options.output);
   +        }
   +        println!("SWAPZ primary zpos is fixed: both layers go to overlays");

   ```

   Whether vc4 accepts a CRTC with its primary disabled and two overlays enabled is for the
   kernel's `TEST_ONLY` to say; not tried.

## Findings for composition-drm (not fixed; for a later item)

1. **Plane list truncated before it is filtered by output.** `planes.truncate(MAX_PLANES)` in
   `crates/composition-drm/src/lib.rs` runs on all 56 planes, after sorting primaries first. On
   BCM2712 the three primaries of unused CRTCs take 3 of the 16 slots, and 4 of the 16 shared
   overlays usable on HDMI-A-1 are dropped. Keeping planes that reach a probed output first, then
   truncating, would give the output 16 usable planes. — observed 2026-11-28 (the count), the fix
   is a suggestion.
2. **Formats truncated to 32, linear first.** The Broadcom modifiers (T-tiled for the RGB formats,
   SAND for NV12/NV21/P030) never reach the engine, and 13 linear formats (XB12 ... S016) are cut.
3. **Rotation not programmed.** The kernel offers rotate-180 and reflect-x/y on every plane; the
   engine reports `transforms 0x0`.

## DriverProfile suggestions (for `profile.rs`; not edited)

What a `Bcm2712Hvs` profile could carry, based on the observations above:

- Scaling: claim scaling on primaries and overlays. 2x up and 1/2 down passed `TEST_ONLY`
  (observed 2026-11-28); the limits beyond that are not measured, so a conservative claim (for
  example up 2, down 2, with `TEST_ONLY` as the final word) fits what was seen.
- zpos: nothing to add; the generic reading (primary fixed 0, overlays mutable 1..=17) matches
  the kernel.
- Blend and plane alpha: nothing to add; all three blend modes and plane alpha are read
  generically and worked on the output.
- Rotation: rotate-180 and reflect-x/y, once composition-drm programs the `rotation` property.
- Plane order: prefer the shared overlays reachable from the probed output over primaries of
  other CRTCs when the list must be cut (see finding 1); this may belong in the generic code
  rather than in a profile.
