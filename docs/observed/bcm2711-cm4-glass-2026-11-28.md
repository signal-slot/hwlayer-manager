# BCM2711 (reTerminal CM4): HVS5 z-order and alpha on real glass, HDMI-A-1 through the NanoKVM (HVS Q11)

Date: 2026-11-28. Rows tagged **observed 2026-11-28** were measured on the board over ssh and through the
NanoKVM HDMI capture of HDMI-A-1 on 2026-11-28 (board clock and host clock UTC, 12:12 to 12:25; the two
clocks agreed to the second). This answers the CM4 display check, Q11 of `docs/design/hvs-backend.md` §11. It
is portability evidence for a Raspberry Pi CM4 (BCM2711, HVS5) only and counts toward no milestone.

**Which glass:** every picture here is the **HDMI-A-1** output as the NanoKVM captures it (CRTC 102,
`pixelvalve-2`, 1920x1080@60). Nobody looked at the reTerminal's own **DSI-1** panel, and no camera points
at it. Everything said about the picture holds for HDMI-A-1 only.

Evidence, all in `bcm2711-cm4-glass-2026-11-28/`:

- `N-<run>.png`: the KVM capture of each run, reduced from 1920x1080 JPEG to 480x270 PNG (the judgement
  was made on the full-size capture);
- `N-<run>.twoplane.log` / `N-<run>.plane_commit.log`: harness stdout (plane_commit's 16 `PLANE` lines left
  out; nothing else removed: the logs have no host, address or serial in them);
- `expect-N-<run>.json`: the camera-check expectation (from `scripts/twoplane-expect.py --rotation 0
  --panel full` for the twoplane runs, written by hand for the plane_commit runs, see §4);
- `N-<run>.camera-check.txt`: `scripts/camera-check.py <capture> <expect> --rotation 0` output;
- `N-<run>.hvs_dlists.txt`: `/sys/kernel/debug/dri/0/hvs_dlists`, read with sudo a few seconds into
  each run (read-only).

## Short answer

- **Z-order on the glass agrees with the programmed zpos and with the dlist order** (observed 2026-11-28). Two
  overlays (planes 127 and 138) overlapping on HDMI-A-1: with 127 at zpos 2 and 138 at zpos 3 the overlap
  shows 138; with the zpos swapped it shows 127. In both cases the HVS channel's dlist lists the planes
  in increasing zpos, and the capture shows the last entry on top. camera-check PASS for both. The
  capture of the swapped run fails against the unswapped expectation on the overlap region only (distance
  332.9), so the check does tell the two orders apart.
- **Alpha on the glass looks as programmed for all three blend modes** (observed 2026-11-28): premultiplied
  with plane alpha 0xffff, coverage with plane alpha 0x8000, and none (pixel alpha ignored, overlay
  opaque). camera-check PASS for the first two. For `none` it gives FAIL at the default tolerance 40 by 0.2
  (distance 40.2 on the magenta regions) and PASS at tolerance 50. The measured colour is opaque magenta
  (222, 0, 232), not a blend: a 50 % blend would be about (144, 16, 144), more than 100 away.
- **No underruns:** `hvs_underrun` was 0 before, during and after every run (observed 2026-11-28). twoplane
  latched 3600 of 3600 frames in each run, with 0 late and 0 dropped.
- Compared with `docs/observed/bcm2711-cm4.md` (DSI-1, `TEST_ONLY` and harness accounting only, glass not
  verified): nothing here contradicts it. The z-order that file only inferred from the dlist and the
  source is now seen on HDMI glass, and the alpha cases that file only saw pass `TEST_ONLY` now show the
  expected colours (§6).

## 2. Getting HDMI-A-1 to a mode the KVM captures

The engine runs on the CRTC's current mode, or on the connector's first mode if the CRTC is off
(`crates/composition-drm/src/lib.rs`, output probe), and fbcon keeps HDMI-A-1 at 640x480@75, which the
NanoKVM does not capture (read from source; observed 2026-11-28). Nothing was changed in DRM, udev, seat
or boot configuration. The mode was switched for the session only, like this:

1. `kmstest -c HDMI-A-1 -r 1920x1080` (from the board's image) with a stdin that stays open, so that it
   holds the mode (it exits at once on an EOF stdin);
2. a root shell opens `/dev/dri/card0` read-only and sleeps (not master, because kmstest is master);
3. `kmstest` is killed with SIGKILL, so it cannot restore. Master is released. The holder keeps the device
   open, so the core's last-close fbdev restore does not run, and CRTC 102 stays active at 1920x1080 with
   no master;
4. each harness run then becomes master, finds the CRTC at 1920x1080 and uses that mode;
5. at the end, killing the holder is the last close, and fbdev restores both outputs (§1 "After").

### dlist words of the overlay entry

Each twoplane dlist (`N-*.hvs_dlists.txt`) has one HVS channel active (channel 1, the HDMI-A-1 path)
with two plane entries: the primary (position word `0x00000000`, size `0x04380780` = 1080x1920), then the
overlay (position `0x010e03c0` = y 270, x 960; size `0x021c0180` = 540x384) (observed 2026-11-28). The
third word of the overlay entry is the one that changes with blend and alpha:

| Run | Overlay word 2 | Primary word 2 | Tag |
| --- | --- | --- | --- |
| 1 premultiplied, 0xffff | `0x2000fff0` | `0x4000fff0` | observed 2026-11-28 |
| 2 coverage, 0x8000 | `0x10008000` | `0x4000fff0` | observed 2026-11-28 |
| 3 none, 0xffff | `0x4000fff0` | `0x4000fff0` | observed 2026-11-28 |

Reading: bits 31:30 are the alpha mode (0 pipeline / per-pixel, 1 fixed), bit 29 premultiply, bit 28
alpha-mix (plane alpha times pixel alpha), and bits 15:4 the 12-bit plane alpha (`0xfff`, and `0x800` =
`0x8000 >> 4`). With that reading, run 1 = pipeline + premultiply, run 2 = pipeline + mix with alpha 0x800,
run 3 = fixed (pixel alpha ignored), and the XR24 primary = fixed. This matches the gen 5 encoding table
in `docs/vc4-hvs-props-source.md` §4.2. Tag: inferred. The bit positions were not read from `vc4_regs.h`
in this session; the `alpha >> 4` scaling is read from source (`docs/vc4-hvs-props-source.md` §4.1).

## 4. Two overlays at explicit zpos, swapped (plane_commit)

`plane_commit --connector 33 --hold-ms 30000` with three `pattern=quadrants` XR24 layers (each buffer is
red top left, green top right, blue bottom left, white bottom right). Connector 33 is HDMI-A-1, and the
CRTC was running, so no modeset was made:

- primary 91: 1920x1080 at 0,0 (zpos fixed 0, not set);
- overlay A = plane 127: 800x400 at 400,200;
- overlay B = plane 138: 800x400 at 800,400.

A's bottom-right quadrant (white) and B's top-left quadrant (red) cover exactly the same rectangle,
x 800..1200, y 400..600. That rectangle is white if A is on top and red if B is on top.

plane_commit's own `EXPECT` lines give only three primary samples. It leaves out every overlay sample,
because it treats the primary (no zpos given) as an "unknown" zpos that covers them (observed 2026-11-28; see
its doc comment). The expectation files `expect-5a-zpos-A2-B3.json` and `expect-5b-zpos-A3-B2.json` were
therefore written by hand from the layout above. They have 11 regions each: four primary quadrants outside
the overlays, three A-only and three B-only quadrants, and the overlap. Rotation 0, `"panel": "full"`,
tolerance 40.

## 5. hvs_underrun

Observed 2026-11-28: `0` before run 1, during runs 1 … 5b (read a few seconds into each) and after the
restore. One 1920x1080 XR24 primary plus up to two overlays (384x540 ARGB, or two 800x400 XRGB) at 60 Hz
on HDMI-A-1, with DSI-1 off, is not near the underrun limit. The load ladder is Q2's subject, not this file's.
