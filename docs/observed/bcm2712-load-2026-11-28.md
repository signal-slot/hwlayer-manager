# BCM2712 (Raspberry Pi 5): HVS load ladder on HDMI-A-1 (HVS Q2, Pi 5 half)

Date: 2026-11-28. Rows tagged **observed 2026-11-28** were taken on the board over ssh between 16:41 and
16:51 host UTC (the board clock and the host clock agreed in UTC). The question is
[`design/hvs-backend.md`](../design/hvs-backend.md) §11 Q2 (bandwidth and underrun): where does the display
count HVS underruns or drop frames while atomic `TEST_ONLY` still passes? Five runs of the
`hvs_load_probe` example (`crates/composition-drm/examples/hvs_load_probe/`) ran on one output, HDMI-A-1
(the only output with a sink, see `docs/observed/bcm2712-two-outputs-2026-11-28.md`, commit
`f16fb63ca7c82da2231c7da3ca778d9531341561`, merged into the integration branch but not on this branch when
this file was written).
They were judged with `scripts/hvs-load-expect.py`. This is portability evidence for SoW §5.4 step 3 only and
counts toward no milestone.

**Short answer (observed 2026-11-28): no threshold was reached.** In 108 of 154 steps `TEST_ONLY` passed and
the real commit ran. In every one of them `hvs_underrun` stayed at 0, every page flip arrived (120/120,
240/240 or 60/60 per step), and no flip was late. The heaviest accepted states were 16 full-screen 1920x1080
XRGB8888 layers, and 4 layers each downscaling 3840x2160 to 1920x1080. All 46 rejections were `err:28`
(`-ENOSPC`) from the LBM or UPM pools, logged by the kernel as `Failed to allocate LBM entry` or
`Failed to allocate UPM entry`. On this board and in this ladder, `TEST_ONLY` rejects resource exhaustion
before any bandwidth limit shows up.

## 4. Why the rejections fall where they fall

A pool model, fitted to the observations above (inferred), with the pool sizes read from source
([vc4-hvs-lbm-upm-source.md](../vc4-hvs-lbm-upm-source.md): UPM 262144 bytes and 32 handles, LBM 1024 lines
on HVS6):

- Each enabled plane holds one UPM block, sized by its source pitch, and one LBM block while it scales
  vertically. It keeps the LBM block after it becomes unscaled, as observed in §3.
- In a step, a plane that needs the same block size it already holds keeps that block. A plane that needs
  a different size counts both its old and its new block. Planes switched off by the step still count their
  old blocks.
- The step is rejected when the UPM bytes exceed 262144, the UPM handles exceed 32, or the LBM lines exceed
  1024.

Applied to every step of the four runs that started from the fbcon state, using the per-plane sizes of the
§3 table, this model predicts accept or reject correctly for all 137 steps: run 1 (102), run 2 (6), run 3
(8) and run 4 (21). The check was a short script run on the host; it is not in the repository (inferred,
computed 2026-11-28). Examples:

- Step 30 (5 x F after 5 x E): LBM 5 x 90 held + 5 x 120 new = 1050 > 1024.
- Step 82 (14 x D after 14 x B): UPM 14 x 4096 + 14 x 15616 = 275968 > 262144.
- Step 97 (17 x A after 16 x B): UPM handles 16 + 17 = 33 > 32. The bytes, 200448, fit, which matches the
  missing kernel line: a handle-count failure is inferred to take a path that logs nothing.
- Run 5, step 17: 17 x 15616 = 265472 > 262144 with nothing else held. The probe's ladder includes the
  primary, so fbcon's 7936-byte block is released.

The one-state-at-a-time limits (no previous blocks held) are what a backend's own accounting would use
(inferred): UPM by source pitch (16 planes at 1920 pixels of XRGB8888, observed in run 5), UPM handles (32),
LBM lines (1024). The double booking during a transition is a second, history-dependent cost. A compositor
that changes many plane sizes in one commit can be rejected below the one-state limit (inferred from §3 and
the model).

## 7. Comparison with the CM4

No `docs/observed/bcm2711-cm4-load-*.md` existed on this branch when this file was written, so there is no
CM4 result to compare. The CM4 has no UPM, and per the prediction its LBM limit is above 16 planes. Its

finding a real underrun threshold (inferred).

## 8. What this does and does not answer

- Q2 on the Pi 5, one output: within everything the HVS accepts on one 1920x1080@60 output, no underrun and
  no dropped or late frame was seen (observed 2026-11-28). On this board the first limit a backend meets is
  LBM/UPM `-ENOSPC`, which `TEST_ONLY` reports correctly. So `TEST_ONLY` was a sufficient check for every
  state tried here.
- Not measured: two active outputs (HDMI-A-2 has no sink), formats other than XRGB8888, YUV and modifiers,
  higher modes (3840x2160 or 120 Hz), and memory load from the CPU or GPU at the same time. A threshold may
  exist under any of these (inferred).
- The flip check counts latched and late page-flip events by kernel timestamp. It does not look at the
  picture, and no KVM capture was taken in this session. An underrun that the HVS does not count, and that
  does not delay a flip, would not be seen (inferred).
- The probe's own restore did not work as designed. In every run, `RESTORE err:22 saved state refused` was
  followed by `RESTORE fallback ok planes off`, so the probe exited with status 1 (observed 2026-11-28).
  fbcon came back by itself when the probe closed the device: plane 83 showed fb 680 `allocated by
  [fbcon]` again after every run (observed 2026-11-28). That the kernel's fbdev client restored it on the
  last close is inferred.
