# STM32MP257F-DK (LTDC): observed display topology and two-plane run

Staging notes for the per-SoC section of `docs/platform-capabilities.md`
(the `caps-doc` item folds them in). Everything here was **observed
2026-11-27** on the board, over ssh, with `probe` and `twoplane` from commit
b0f3ef3 cross-built on the host. Nothing here is read from source; where a
line is a conclusion it is tagged **inferred**.

Dates are UTC from the build host's clock. The board's own clock was not
NTP-synchronised during the session and ran about ten hours behind, so the
`DATE` lines the harness printed on the board say 2026-11-27T08:xx; the host
clock said 2026-11-27T18:xx UTC.

## How it was run

- Build: `cargo build --release --target aarch64-unknown-linux-musl -p composition-drm --example probe --example twoplane --config 'target.aarch64-unknown-linux-musl.linker="rust-lld"'`.
  Rust's own `rust-lld` as linker, static musl binaries, no C cross toolchain.
  `scripts/cross-aarch64.sh` was not used.
- The binaries went to `/tmp` on the board only and were removed afterwards.
- What ran before: `seatd-weston.service` and `weston-graphical-session.service`
  (Weston as user `weston`, with `weston-desktop-shell`, `weston-keyboard` and
  ST's GTK demo launcher `demo_launcher.py`). Weston held DRM master; the
  primary plane showed a Weston framebuffer, both overlays were off.
- `probe` and `modetest -p` ran with Weston up (they read only). For the
  `twoplane` runs `weston-graphical-session` was stopped, and it was started
  again at the end: `systemctl is-active weston-graphical-session seatd-weston`
  printed `active` twice, Weston, its shell and the demo launcher were running
  again, and the primary plane showed an fb "allocated by = weston".
- No serial console, reset, U-Boot, boot partition or eMMC access. Nothing
  installed on the board.

```text
RESULT frames=600 committed=600 latched=600 released=1198 dropped=0 late=0 period_ms=16.667 latch_interval_mean_ms=16.667 latch_interval_max_ms=17.421 elapsed_s=9.997 swapped_at=300
RELEASE after the run: released 1200 of 1200 buffer uses, 0 still on screen
VERDICT twoplane: PASS 600 frames on two planes, 600 latched, 1198 released, 0 late, driver stm mode 1920x1080@60.000Hz
```

Atomic state in the second half: plane 34 crtc-pos 384x540+960+270
normalized-zpos 0, plane 42 crtc-pos 1920x1080+0+0 normalized-zpos 1, no
underruns. So the planner did the swap by **moving the layers between
planes** (the overlay onto the primary plane, the background onto plane 42),
not by writing crossed zpos values; the zpos of each plane stayed 0 and 1.
The swap itself worked (committed and latched without a dropped frame), but
the run did **not** exercise reprogramming the zpos property (inferred from
the plan lines and the normalized-zpos values above).

## KVM result

**No picture: the KVM could not be used.** The NanoKVM's MCP server failed to connect for this session (HTTP 404 from
the relay), so no screenshot was taken, and z-order and alpha were **not**
verified on the physical output. Evidence held instead, all from the board:

- the kernel's atomic state during the runs (plane, fb owner, crtc-pos,
  normalized zpos, LTDC underrun counters) as quoted above;
- the harness's own event accounting (every frame latched, no drop, no late
  latch);
- the `EXPECT` lines, which a later KVM run can compare with
  `scripts/camera-check.py`.

The colours on screen remain unchecked. A rerun with a working KVM should
take one screenshot in each `--swap-z` phase (about 2 s and 7 s into a
600-frame run) and one with `--plane-alpha 32768`.

## DriverProfile suggestions (not applied)

For a future `DriverProfile::Stm32Ltdc` in `crates/composition-drm/src/profile.rs`,
following the `Imx95Dpu` pattern:

- **Scaling: upscaling only.** TEST_ONLY took a 2x upscale and refused a 2x
  downscale on every plane candidate. Claiming upscaling with
  `max_downscale = 1.0` would let the planner use it. The upper bound was not
  measured (only 2x was tried); take it from the ST source notes before
  setting it. Which planes scale was not isolated either: the harness only
  reports that some candidate passed (inferred: at least one of the three).
- **Blend: premultiplied only**, as composition-drm already reports when the
  `pixel blend mode` property is missing. No change needed, but an ARGB
  overlay that must ignore its alpha has to be given an XRGB buffer.
- **Transforms:** the kernel lists rotate-90/180/270 on plane 34 and the two
  reflections on every plane; composition-drm reports and programs none
  (`transforms 0x0`). That is a composition-drm feature gap rather than a
  profile item.
- **Plane 49 has no YUV formats**; the format lists already say so, so no
  profile rule is needed.

## Harness notes

- `--swap-z` on this driver swaps plane assignments rather than zpos values
  (see above), so "zpos is mutable" is shown by the caps but not exercised by
  a commit. A swap that keeps each layer on its plane and writes crossed zpos
  values would need a planner preference or a harness option; this is new
  work for the harness item, not a bug, and no diff is proposed here.
- No harness bug was found in these runs.
