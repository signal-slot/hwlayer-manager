# VC4 / HVS topology, read from Raspberry Pi kernel source

Staging file for a later fold into `docs/platform-capabilities.md`. Nothing here was measured on a board. Rows are tagged:

- **source**: read from the driver source. Not run.
- **inferred**: a conclusion drawn from the source, not stated by it.

## Provenance

- Tree: `raspberrypi/linux`, default branch `rpi-6.18.y`, commit `16ae2649dcfadf9d81445b1177a3191efa3cb82e` (committer date 2026-11-26; the commit itself touches only `drivers/staging/media/hevc_d`, not vc4). Read on 2026-11-28.
- Driver: `drivers/gpu/drm/vc4/` (`vc4_crtc.c`, `vc4_hvs.c`, `vc4_kms.c`, `vc4_plane.c`, `vc4_txp.c`, `vc4_drv.c`, `vc4_drv.h`, `vc4_regs.h`).
- **How it was read, and its limits.** The shallow sparse clone into the dependency cache and `curl` were refused on the machine that wrote this, so no checkout exists. The files were fetched as raw text from `raw.githubusercontent.com/raspberrypi/linux/rpi-6.18.y/...` through a web-fetch helper. That tool returns no line numbers, so references below are **file + function**, not line. The fetch tool also truncates quotes, so most rows are paraphrases of text that was read, not copies. `vc4_plane_init` and `vc4_plane_create_additional_planes` (end of `vc4_plane.c`) were read verbatim in the first helper run; `vc4_hdmi.c` was read only for its first ~39 kB, so its match tables and the HDMI/DSI/DPI/VEC compatibles are **not** verified (marked below). A later reader with a real checkout should re-check each row against `git -C <checkout> grep` before it moves into `platform-capabilities.md`.
- Which branch a board runs is not known from this file. Distribution kernels (Raspberry Pi OS, Torizon, Yocto `linux-raspberrypi`) may sit on a different `rpi-6.x.y`; plane and format details can differ.
- Generation names in the code: `VC4_GEN_4` (BCM2835/6/7), `VC4_GEN_5` (BCM2711, HVS5), `VC4_GEN_6_C` and `VC4_GEN_6_D` (BCM2712, HVS6 steppings C0 and D0). D0 is detected at bind by `SCALER6_VERSION == 0x54` (`vc4_hvs_bind`).
- Compatibles: core `brcm,bcm2711-vc5` / `brcm,bcm2712-vc6` (`vc4_drv.c`); HVS `brcm,bcm2711-hvs` / `brcm,bcm2712-hvs`.
- Not in scope here: BCM2835 (gen 4), and firmware KMS (`vc4-fkms-v3d`), which skips the driver paths below. This file assumes full KMS (`vc4-kms-v3d`).

### BCM2711: what this means for the project (inferred)

- Two real hardware planes on one output are available: the primary (zpos 0) plus any of the shared overlays (zpos 1..16) and the cursor plane (zpos 17). Alpha, three blend modes and an overlay-range zpos are all present.
- The overlay pool is shared between CRTCs. A planner that reads `possible_crtcs` per plane sees all 16 as usable on either HDMI output; the dlist and LBM are what bound them. This looks like a resource-group shape similar to `Imx95Dpu` (shared pool), but the limiting resource here is dlist words and LBM, not fetch units, and `TEST_ONLY` is the only way to see the failure.
- Primary planes have an immutable zpos 0 and a cursor plane is always on top. A compositor that wants the "video on a lower plane than the UI" order has to put the video on the primary and the UI on an overlay, or accept the opposite.
- Modifier use needs care: a SAND or T-tiled buffer must be one of the listed (format, modifier) pairs; other pairs are rejected by `vc4_format_mod_supported`.

### BCM2712: what this means for the project (inferred)

- Two hardware planes on one output are available exactly as on BCM2711, with the same zpos, alpha and blend properties.
- The planner needs per-modifier knowledge: T-tiled and SAND64 are advertised in the plane's `IN_FORMATS` list at the property level but the driver filters them per generation (`vc4_format_mod_supported`), so what a probe on a Pi 5 shows is what counts. If the probe lists them, the `IN_FORMATS` blob and the source disagree, and that is worth recording.
- The 2712 has only 2 display CRTCs, so overlays are shared between just two outputs.
- With no software bandwidth check on gen 6 and none enforced on gen 5, a commit that the HVS cannot sustain fails at runtime (underrun, dropped frames) and not in `TEST_ONLY`. Only the dlist, LBM and UPM allocations and the per-plane checks are visible to `TEST_ONLY`. This matters for the SoW test of "unsupported combinations".

## Cross-generation notes (inferred)

- **What `TEST_ONLY` can and cannot see.** Visible: format/modifier support, scaling limits, LBM and UPM allocation failure, dlist allocation failure, channel assignment failure, more than one connector on a CRTC. Not visible: real memory bandwidth, underrun.
- **Where capability detection (static property reads) falls short.** The overlay count (16 per allocation) says nothing about how many fit in the dlist; the formats list is per plane but identical across planes; T-tiled availability depends on generation.
- **Candidate `DriverProfile` resources if one is added later.** Shared pool of overlay planes (one pool across CRTCs), LBM scaling units (vertical-scaled planes), UPM handles (gen 6, one per colour plane), dlist words.
