# BCM2711 (Raspberry Pi CM4, reTerminal): probe and two-plane harness

Staging file for a later fold into `docs/platform-capabilities.md`. Rows tagged
**observed 2026-11-28** were measured on the board over ssh on 2026-11-28 (local date; the harness
prints UTC, `DATE 2026-11-27T18:3xZ` for the first session and `18:4xZ` for the re-run on commit
112648f, see "Re-run on 112648f"). "source" rows refer to `docs/observed/vc4-hvs-source.md` and
are kept apart from the observed ones. "inferred" rows are conclusions, not measurements.

The topology-only run of the same board is `docs/observed/bcm2711-cm4-topology.md`; this file adds
the two-plane harness (`crates/composition-drm/examples/twoplane.rs`) and a correction to the plane
count seen there.

> **Physical output not verified: no KVM.** Nothing captures the reTerminal's DSI panel, and nobody
> looked at it. Z-order and alpha on the glass are **not** verified. The evidence below is the
> harness's event accounting, the kernel's `TEST_ONLY` answers and the driver's own atomic state and
> HVS display list read from debugfs. The `EXPECT` lines give what a camera or capture would have
> to show; they were not checked.

## DriverProfile suggestions (not applied; `profile.rs` untouched)

- **Scaling.** The kernel accepted scale-up and scale-down in `TEST_ONLY`; the source has PPF / TPZ
  scaling on every non-cursor plane, with no fixed DRM-helper limit and a driver limit far above
  16× (`SCALER_TPZ0_SCALE_MASK`). A `Vc4Hvs` profile could claim scaling on primaries and overlays,
  e.g. up and down by 16 (what the harness's hand-built plan claimed and the kernel took). The real
  bound is LBM and dlist space, which only `TEST_ONLY` sees; keep relying on it.
- **Shared overlay pool / dlist.** The 16 overlays are one pool for all non-TXP CRTCs (source); with
  one output active nothing is contended. A resource group like `Imx95Dpu`'s only matters with two
  outputs, which this board cannot show (both HDMI unplugged). Not observed; do not model yet.
- **Plane enumeration (more important than a profile).** On vc4 the kernel exposes 60 planes and the
  engine keeps 16 chosen by kind, not by reachability: five slots go to primaries of other CRTCs,
  six reachable overlays and the cursor are lost. Proposed change to `crates/composition-drm/src/lib.rs`
  (not applied: out of this item's scope):

  ```diff
  -        // Primary first so that the bottom layer lands there by preference.
  -        planes.sort_by_key(|(_, p)| match p.caps.kind {
  -            PlaneKind::Primary => 0,
  -            PlaneKind::Overlay => 1,
  -            PlaneKind::Cursor => 2,
  -        });
  +        // Planes that reach a probed output first, then primary first so that
  +        // the bottom layer lands there by preference. Only MAX_PLANES are kept.
  +        planes.sort_by_key(|(_, p)| {
  +            let kind = match p.caps.kind {
  +                PlaneKind::Primary => 0,
  +                PlaneKind::Overlay => 1,
  +                PlaneKind::Cursor => 2,
  +            };
  +            (p.caps.outputs == 0, kind)
  +        });
  ```

  With it this board would get 1 primary + 15 overlays on output 0 (still one short of the 16
  overlays and the cursor, because of `MAX_PLANES = 16`). Whether the `conventional` overlay zpos
  numbering after the sort needs the same order was not checked.
- **Fixed primary zpos.** The primary is immutable 0 and every overlay mutable, so `--swap-z` is
  always skipped on vc4 while the planner puts the bottom layer on the primary. A z-swap test on this
  driver needs two overlays.

## Harness notes

- With `--swap-z` the harness prints the `EXPECT phase=swapped` lines before it finds that the swap
  cannot be done (`SWAPZ skipped`), so the output carries expectations for a phase that never ran.
  Proposed: print the swapped `EXPECT` block only when the swap is going to happen, or tag them
  `skipped` after the `SWAPZ skipped` line. Not a correctness problem in the run itself. Tracked
  as X-08 in `docs/open-issues.md`.
- The `layers` combination reports "11 planes on the output" from the truncated plane list (above).
  The plane enumeration is tracked as X-09 in `docs/open-issues.md`.
