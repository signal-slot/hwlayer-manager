# M3 AM62P board session: risk and fallback register

Written 2026-11-28, before any board session. It lists what can go wrong in the M3 session on the Verdin AM62P: the R5F image started through remoteproc, the trace buffer as the console, camera photographs, then a reboot into Torizon. It makes no hardware claim. No AM62P board observation exists in this repository yet, so every likelihood is a judgement, not a measurement.

## What this register is based on

Tags in the last column:

- **source**: read in a document named in the entry.
- **inferred**: the register's own reasoning from those documents or from general practice. Check it against the board.

Documents read:

- `docs/board-test-am62p-r5f.md`, as on branch `work/am62p-board-test` (tip 361e31f). It is not on `main` yet, so it is named here without a link. Its "Run" section is the only description of the remoteproc route in this repository.
- `$MCUI_SHOWCASE_DIR/docs/remoteproc-bringup.md` is the demo's own document, outside this repository. It was **not read**. Everything about "what to stop or unbind" below rests on the board-test document's one-sentence summary of it.
- `docs/board-scenarios.md` (the AM62P board rule at its end; the i.MX95 remoteproc script's exit codes as an analogy).
- `docs/twoplane-backend.md` and `docs/am62p-imx95-matrix.md`: the AM62P column is "not recorded" for the Linux DRM side and for ownership.
- The planned source studies (`docs/am62p-*-source.md`, `docs/am62p-torizon-boot-source.md`) and `docs/m3-am62p-test-plan.md` were **not present** on the tip this was written on. Entries that need them say so. Re-read this register when they land.

Likelihood is low, medium or high for the M3 session as planned. Fallback means what the agent does on the spot. The rule that wins over every fallback: the session ends with the board on its Torizon boot chain and confirmed over ssh (project rule, 2026-11-25; also `docs/board-scenarios.md`, last section).

| R1 | **The board stops answering** (ssh times out during or after the R5F start). There is no remote power control. | Medium. | R7 | **Torizon does not come back** after the reboot. | Low to medium. The route leaves the boot chain alone, per the board-test document. No other boot route is tried from this session. State what is known (last command, time), say Torizon is **not confirmed**, and name the project rule it breaks. The owner restores the board by hand. | The rule is source (project rule 2026-11-25; `docs/board-scenarios.md`). Likelihood and the boot chain: inferred. |
| R8 | **The serial console is busy** (`resource:serial-am62p`). | Certain, as the plan stands. | The plan marks the serial resource as busy. | The trace buffer is the console. The serial console is an optional extra, used only if it is free and only to read. A run that depends on it is not started. Nothing in the report depends on it, so its absence is not a failure. If R2 happens (empty trace) and the serial console is busy, the run has no console: use the photographs (R4, R5). | source for the trace buffer as the console (board-test doc, "Run"). ## Order of fallbacks

1. R1 and R7 end the session at once, with a report. They are the only entries whose fallback is "stop".
2. R2, R3, R4, R5, R10 end the run, not the session. Collect, restore, reboot to Torizon (R6, R7), then decide on one fixed image.
3. R8 changes nothing in the plan.
4. R9 is checked before every reboot.
