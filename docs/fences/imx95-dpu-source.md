## Answers

Short form: the driver is a plain atomic-helper driver. Explicit in-fences, out-fences and implicit sync all come from DRM core and its helpers; the driver adds nothing of its own to the KMS path, and its CRTC code never touches a fence.

| When is the OUT_FENCE signalled? | By the CRTC's vblank event, not by a release. Here the event is sent from the DPU frame-complete interrupt (`dpu95_crtc_dec_frame_complete_irq_handler`, which also calls `drm_crtc_handle_vblank`), or from `atomic_disable` when the CRTC turns off with an event pending (`crtc->state->event && !active`). The event is parked by `dpu95_crtc_queue_state_event()` (called from `atomic_flush`, `atomic_enable`) and sent at the next frame-complete interrupt after the ExtDst shadow load. So the out-fence means "this commit's state is now live / latched at a frame boundary", **not** "the previous buffer is no longer read". ## What this means for the engine (inferred from the rows above)

- **inferred**: an in-fence handed to `IN_FENCE_FD` is waited for by DRM core before the hardware is written, so §3.2 of `docs/sync-fences.md` ("the kernel waits, the engine does not") holds on this driver without driver work. Whether a real producer's fence reaches that wait on this board is not shown by source.
- **inferred**: because `prepare_fb` is the GEM helper on all planes, a client that renders with a GPU into a dma-buf and gives no explicit fence still gets implicit sync from the buffer's `dma_resv`, and a client that gives an explicit fence turns the implicit write fence off (`DMA_RESV_USAGE_KERNEL` only). The engine must not pass both and expect both to be honoured.
- **inferred**: `OUT_FENCE_PTR` here reports "latched", at the frame-complete interrupt. It is the right source for the "latched" event of SoW §7 and a poor source for "released".
- A zero-copy path where the producer is a different driver (GPU, VPU, camera) depends on that driver publishing fences in the dma-buf; nothing in `dpu95` checks this.

## Not read, not claimed

- The GPU / VPU / camera sides, and the dma-buf allocator of the board's userspace.
- Any runtime behaviour: timing of the out-fence relative to scanout, fence-wait cost, behaviour when a fence never signals on this board.
- `dpu95-plane.c` atomic_update details unrelated to fences.

## Checks for the M1 board run (plan #453)

Each is a check on the board with the stock kernel; tag a result as observed, with its date, only if it was run on the board.

1. **Properties present at run time.** Re-list properties and confirm `IN_FENCE_FD` on every plane in use and `OUT_FENCE_PTR` on the active CRTC (the recorded probe shows both on 2026-11-28; the run must show them again on the kernel it uses and record `uname -r`, which must read `6.6.157-7.8.0` for this document to apply).
2. **Kernel matches the source read.** Check that the running kernel's version is the one pinned above before any claim "as read from source" is carried over; a different version string means this file does not apply without a re-read.
3. **TEST_ONLY with an in-fence.** `DRM_MODE_ATOMIC_TEST_ONLY` commit with `IN_FENCE_FD` set to a valid unsignalled sync file on the primary plane: expect success. TEST_ONLY with an invalid fd: expect the kernel's error from the property setter.
4. **Real commit with a pending in-fence.** Blocking commit with an unsignalled fence from a controlled producer (a sync file the test signals itself after a known delay): the ioctl must not return before the signal, and scanout must not change before it. Record the measured time between signal and the out-fence/event.
5. **In-fence is waited in NONBLOCK too.** The same with `DRM_MODE_ATOMIC_NONBLOCK`: the ioctl returns at once, the commit completes only after the signal (flip event arrives after, not before, the signal). This is `commit_tail`'s wait.
6. **Already-signalled fence.** A signalled fence adds no measurable delay beyond a commit without one.
7. **Fence that never signals.** With NONBLOCK and a fence that is never signalled: the commit must stay pending, a later commit touching the same CRTC must be refused (`EBUSY`) or queued as core decides, and the engine's own timeout path (§3.1 of `docs/sync-fences.md`) must be the thing that recovers. Do not run a blocking commit with such a fence unattended; core has no timeout.
8. **OUT_FENCE_PTR.** Set `OUT_FENCE_PTR` on the active CRTC to a valid user address: the returned fd must be a sync file that signals at the commit's flip event; record order and time difference of the fd signal and the `DRM_EVENT_FLIP_COMPLETE` event (read from source says they come from the same event send). Also check the fd is `-1`/unset on a `TEST_ONLY` commit.
9. **Out-fence on CRTC off.** Commit that disables the CRTC with `OUT_FENCE_PTR` set: the fence signals from the disable path (`crtc->state->event && !active`); confirm it signals and is not left pending.
10. **Implicit sync, positive.** Render into a dma-buf with a producer that publishes a write fence (a GPU client, if the board image has one), then commit without `IN_FENCE_FD`: the commit must wait for the render. Record whether it did. If the board has no such producer, record that this check was not possible, rather than inferring it.
11. **Explicit overrides implicit.** With a dma-buf that has a pending write fence and an already-signalled explicit `IN_FENCE_FD`: the commit must not wait for the implicit write fence (`DMA_RESV_USAGE_KERNEL` only). Mark this check `inferred` unless a producer that holds a write fence is available.
12. **One event slot.** Two back-to-back NONBLOCK commits with events on one CRTC: check there is no `WARN_ON` in the kernel log from `dpu95_crtc_queue_state_event` and that both events arrive, in order.
13. **Release.** Confirm what "released" can be observed as: after the commit that replaces buffer A with buffer B, A's reuse is safe once B's flip event (or B's out-fence) has fired and not before; check with a reader of A that is slowed on purpose. This is the only check for the SoW §7 "released" event and the source does not show it.
14. **Out of scope on this board path.** Do not claim async page flips (not supported, row above), nor blit-engine fences, from this run.
15. **Claim hygiene.** Results from checks 1 to 14 count as observed only if run on the board; M1 is not claimed from this file, host tests or vkms.
