# Mapping the advisory planner onto libliftoff's API (WP5)

Written 2026-11-28. This is desk work for the WP5 upstreaming proposal. It maps `composition_core::advise`, the C function `ce_advise` and the `DriverProfile` data onto the public API of libliftoff, concept by concept, and says what form an offer could take. It offers nothing yet, promises no upstream acceptance, and nothing in it ran on a board.

## 1. The two models in one paragraph

libliftoff (MIT, **read from source (2026-11-28, c4226a7)**, gap analysis) owns a DRM fd, a list of planes and, per CRTC, a list of "layers" (virtual planes with arbitrary KMS properties). `liftoff_output_apply` searches for the allocation that puts the most layers on planes, by depth-first search over planes with an atomic `TEST_ONLY` commit at each node, under a wall-clock deadline (default 1 ms). It fills a caller-owned `drmModeAtomicReq` and the caller commits. What does not fit is "needs composition", and the caller composites it. The advisory planner (Apache-2.0, **read from source (this repo)**) takes a snapshot of capabilities, buffer metadata and a frame, and returns per layer: on a plane, composed, or hidden; plus one composition target; plus a reason. It owns no fd, commits nothing and keeps nothing between calls. Both answer "which layers can go on planes, and what is left for the compositor". They differ in what they take, how they search, how they stop and what they say about a refusal.

## 2. Concept map

"Counterpart" says whether libliftoff has the concept. "Form" is what an offer of **this repository's** side could take: **hint API** (a call or option added to libliftoff), **profile file** (data a libliftoff user loads), **helper** (a separate program or library that sits next to libliftoff and is not part of it). Every "Form" is **inferred**; none has been discussed with the libliftoff maintainers.

### 2.2 Concepts of the advisory contract

| Concept (advisory side) | libliftoff counterpart | What an offer could be (inferred) |
| --- | --- | --- |
| **Typed reason per refused layer.** `CE_REJECT_*` bit set (`OUTPUT`, `FORMAT`, `SCALING`, `SOURCE_SIZE`, `ALPHA`, `BLEND`, `TRANSFORM`, `FULL_OUTPUT`, `Z_ORDER`, `RESOURCE`, `IN_USE`) and a `CE_BLOCKER_*` class (`STATIC`, `COMBINATION`, `BACKEND`, `CLIP`, `BUDGET`) | None. libliftoff returns a boolean per layer; the reason goes to the debug log as text (gap analysis rows "Reasons for refusal", **c4226a7**) | **Hint API**, smallest form: a per-layer query such as "the last apply refused this layer on plane P because of property X". This is the gap-analysis item "contribution candidate as an idea". Only a sketch; not designed against libliftoff's search structure, which this item did not re-read |
| **Per-plane static reasons without a search** (`ce_explain_layer`, `advise::explain_layer`) | None | A **helper** is more natural than a libliftoff change: it needs plane data, not the search |
| **Composition model.** One contiguous run of stacking positions is composed into one target; the target is a full-output layer; runs tried shortest first, lowest first | `liftoff_output_set_composition_layer(output, layer)` (**c4226a7** header): one composition layer per output, "won't be used if all other layers have been mapped", valid on the primary plane only; `check_alloc_valid` refuses an allocation that uses the composition layer when everything fits (**c4226a7**, notes section 8) | Both have a single composition target per output. libliftoff's is a caller-created layer the search may place on the primary; advise's is a synthetic layer whose position and plane are part of the answer, and the composed set is constrained to a contiguous run (`advisory-planner-design.md` §2.1, decision §6.1). The two compositions are not the same function: advise says which run to compose, libliftoff says which layers it could not place around a composition layer. No offer follows from this row; it is where a cross-check is needed |
| **Hidden layers.** Entirely off the output: no plane, no composition | Invisible layers (`alpha` 0, or `FB_ID` 0): skipped by the search, `needs_composition` false (**c4226a7**, notes section 4) | Same effect, different trigger. libliftoff does no geometry test (no clipping seen in `alloc.c`, gap analysis row "Clipping to the output") |
| **Exact clipping or refusal** (`CE_BLOCKER_CLIP` when a layer cannot be clipped exactly) | Not seen in `alloc.c`; the cross-check model refuses any destination outside the output, which is the design's v1 restriction, not libliftoff's rule (report, "Harness limits") | None. Not offerable to libliftoff, which hands geometry to the test commit |
| **Layer priority.** advise has none: minimal composed count, ties to the lowest run; `Layer` has no priority field (`advisory-planner-design.md` §6.3) | Internal only: `current_priority` rises when a layer's `FB_ID` changes, folded in every 60 applies, and orders the layers in `update_layers_order` (**c4226a7**, notes section 9). **No public priority setter**: the `c4226a7` header, read first hand, exposes none (the internal priority is per the notes) | libliftoff's priority is an update-rate heuristic, not a caller's weight. A caller-weighted priority would be new in both libraries. Open decision §6.3 of the design; not an offer |
| **Reuse across frames.** advise is stateless: the same input always gives the same advice (§6.8); no cache | `reuse_previous_alloc`: reuses the previous mapping with one test commit when nothing material changed (`layer_needs_realloc`) (**c4226a7**) | libliftoff has it, advise does not. The gap analysis lists it as an idea to take over *if* benchmarks show planning cost matters. Nothing measured. This is the stateful `Engine::advise` question, not part of the stateless offer |
| **zpos handling.** advise plans zpos assignments, including restacking planes with a mutable `zpos` range | libliftoff **never programs `zpos`**: it reads the plane's current value and uses it only to order planes and decide which layer may use which plane (`plane.c`, `alloc.c`, **c4226a7**, crosscheck design section 2) | Real difference of contract. In the cross-check it produced core-only frames on planes with a `zpos` range (S7-3: pinning every plane's zpos made all 21 swept frames both-reject; report). Whether a given driver accepts such a restack in one commit is a hardware question the host run cannot answer |
| **Intersection-aware zpos.** advise orders by stacking and plane `zpos` | libliftoff preserves relative zpos only between intersecting layers (`layer_intersects`, `check_layer_plane_compatible`, **c4226a7**) | The gap analysis lists "adopt intersection-aware zpos" as an idea for this side, not an offer to libliftoff |
| **Step budget, deterministic.** | Deadline in nanoseconds, so results can differ with load | Report: "no `unstable` frame" with `INT64_MAX` timeout; the default 1 ms deadline was **not exercised** |

### 2.3 Contract difference (the SoW §4.1 point, restated against the API)

- libliftoff's `liftoff_output_apply` returns the **best partial allocation** and leaves the rest to the caller. `ce_advise` returns the same kind of result when `compose.enabled` is set. With `compose.enabled == 0` a frame that does not fit is still `CE_OK` with every layer `CE_PLACE_COMPOSE` (decision 13 of the design). The planner underneath (`planner::plan`) is all-or-nothing, `ce_present` is binding, and `Advice` cannot be committed. So the all-or-nothing contract the gap analysis calls "the deciding difference" is true of `plan` and `ce_present`, not of `advise`. **Inferred:** the justification for not reusing libliftoff therefore rests on the other points (section 4), not on the contract of the advisory entry point.
- libliftoff never touches the display itself but does need an owned DRM fd with atomic enabled; advise needs neither.

### 2.4 `DriverProfile` data

`DriverProfile` (**read from source (this repo)**, `crates/composition-drm/src/profile.rs`) has variants `Generic`, `Imx95Dpu`, `Stm32Ltdc`, `Rk3588Vop2`, `Vc4Hvs5` and `Vc4Hvs6`. `apply(&mut Capabilities)` adds what KMS does not carry: scaling limits, source-size limits and **resource groups** (hardware units shared between planes, filled by trait: `SCALED_H`, `SCALED_V`, `YUV`, `ANY`). For `Imx95Dpu` the doc comment says: six planes, at most six active across both display streams (the `ANY` group), four fetch units that can take YCbCr or feed a scaler, and that **none** of the resource groups is observed, since KMS never shows them; they come from driver source and must be confirmed by `TEST_ONLY` on the board.

| Profile concept | libliftoff counterpart | Form (inferred) |
| --- | --- | --- |
| Per-plane scaling limits, source-size limits | None. libliftoff "knows nothing about scaling limits, source or destination size limits" and leaves them to the test commit (crosscheck design section 2, **c4226a7**) | **Profile file**, as data a libliftoff caller could load to pre-filter planes before the commit. Requires a format and a loader in a C library with no profile concept; an upstream change, not an add-on |
| Shared resource groups with capacity per trait | None | The same. Report: scaling knowledge is the single largest source of disagreement: all 72 / 40 / 58 `structural` liftoff-only frames of the three sweeps disappear under `full`, where the model carries the profile (report, "Triage", S7-10) |
| A per-driver table | Not generic KMS | `wp5-gap-analysis.md` W5-09 already says it may stay project-local. **Inferred:** the data is keyed by driver name and is kernel-version dependent, which fits a **helper** or an out-of-tree file better than a libliftoff table. Whether libliftoff's maintainers want any per-driver data is unknown; nobody has asked |

All profile numbers other than the ones tagged observed in the `Imx95Dpu` comment come from driver sources of one kernel version; none is measured on a second board.

## 3. Forms an offer could take, ranked (all inferred)

1. **Out-of-tree helper (no libliftoff change).** The repository publishes `composition_core::advise` / `ce_advise` and `DriverProfile` as they are, under Apache-2.0, and documents how a libliftoff user can call `ce_advise` next to `liftoff_output_apply` (for example to explain a refusal). Needs nothing from the libliftoff maintainers. Weakness: it duplicates libliftoff's capability reading unless a converter exists (table 2.1, row 2).
2. **Hint API in libliftoff.** A narrow addition: per-layer refusal reason after `liftoff_output_apply`. Needs the maintainers' agreement, a design against `alloc.c` that this item did not make, and an MIT-licensed implementation written for libliftoff (the code would be new C, not a port of the Rust, since libliftoff is C with `malloc`). Licence and sign-off questions: `docs/wp5-proposal.md` (a separate item; not linked or edited here).
3. **Profile file.** Largest change: a data format, a loader and a semantic of "resource group" that libliftoff lacks. Ranked last because of size, and because W5-09 already doubts that per-driver data belongs upstream.

None of these is decided. They are for the owner (`advisory-planner-design.md` §6, and the upstreaming proposal).

## 4. What this mapping says about "why not reuse libliftoff" (SoW §4.1)

Only evidence that exists is used.

| Argument | Evidence | Strength |
| --- | --- | --- |
| Memory model: libliftoff allocates per apply (`malloc`, `calloc`), keeps linked lists and reads `CLOCK_MONOTONIC`; the engine is `no_std`, bounded, caller-provided storage, so it can build for `thumbv7em-none-eabihf` | **read from source (c4226a7)** for libliftoff; the two `thumbv7em` builds are CI steps of this repo (`docs/ci.md`) | Statement of fact on both sides. That libliftoff **cannot** be made `no_std` was not tested; **inferred** only |
| libliftoff needs an owned DRM fd with atomic enabled; the engine has none | **read from source (c4226a7 header)** | Fact. Whether the MCU target needs a planner without DRM is the project's own premise (SoW §3.2, §5), not a measurement |
| Typed refusal reasons, per-plane static reasons | libliftoff returns bool plus log text (**c4226a7**) | Fact on libliftoff's API. Value to a compositor: **not measured** |
| Buffer lifecycle (latch, release) | libliftoff has no such API (**c4226a7**) | Fact. It concerns `Engine`, not `advise` |
| Resource groups and scaling limits in the planner | libliftoff has none (**c4226a7**); cross-check shows the structural-only mode of this planner produces the same S7-10 gap | Shows that the **test commit**, not the planner, must carry this knowledge in libliftoff. The report ran a model of the kernel, not a kernel |
| Same answers on common ground | Cross-check: `fill`, `zperm`, `fmt`, `tie`, `alpha0` families agree on every swept input; differences sit in `rand` and `scale`, and all are triaged, one is a lead (L-1) | Host-run evidence on a fake kernel. Not a hardware or parity claim |
| **Speed** | `docs/host-metrics.md` times only this planner's `Engine::validate` on the fake backend. **No libliftoff timing exists in this repository** and the cross-check report measured none | **not measured** |
| **Fewer allocations / lower memory** | None beyond `size_of` pins on the host side; libliftoff's allocation count was not measured | **not measured** |
| **Better allocations** (more layers on planes) | The cross-check compares agreement against a model, not the number of layers placed on a real device | **not measured** |
| **Lower power or latency on a board** | No board run of either planner | **not measured** |
| Reuse across frames favours libliftoff | `reuse_previous_alloc` exists there, not here | Fact; its benefit was not measured either |

So the evidence supports "different memory model, different inputs, additional reasons API, no buffer lifecycle in libliftoff" and does not support any performance or allocation advantage. Proposal text must not claim one. **Inferred:** the section 2.3 finding (advise already returns a partial answer) means the SoW §4.1 text should not lean on "all-or-nothing" for the advisory entry point; that sentence is true of `plan` and `ce_present`.

## 5. What an upstream offer still needs (for the proposal item and the owner)

- **A first-hand read of `alloc.c` and `layer.c`** at `c4226a7` (section 0; only the header was read first hand). Without it, the search, reuse and priority rows rest on earlier notes. The same applies to any claim about libliftoff's current priority or reuse code.
- **Owner decisions** of `advisory-planner-design.md` §6 (they stay open), and the licence and sign-off route for any contribution (Apache-2.0 code in this repository, MIT in libliftoff; see the proposal item and the contribution-rules item).
- **Cross-check on board data and a benchmark** (WP5-04/06) before any speed, allocation or placement-quality sentence is written.
- **A design of the hint API against `alloc.c`**, if form 2 is chosen: this document names the idea, not the change.
- No acceptance by libliftoff's maintainers is implied or expected; nobody has been contacted.

## 6. What this document does not claim

- Nothing was measured; no timing, allocation or power figure appears except where the report's host counts are quoted.
- Nothing ran on a board; no hardware claim.
- Only `include/libliftoff.h` of `c4226a7` was read first hand; `.c` behaviour is second hand (section 0).
- The forms of section 3 are proposals, not agreements.
