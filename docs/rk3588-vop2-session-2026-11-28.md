## Q1. Does MAX_FORMATS=32 hide AFBC pairs on Cluster planes? Is linear first?

**Answer: yes, it hides most of them. Linear is not first, because it is not listed at all.**

- Each Cluster plane (33, 39, 45, 51) lists 14 formats x 9 modifiers = 126 (format, modifier) pairs (observed 2026-11-28; `kms_sweep` prints "in_formats 126 pairs"). Each Esmart plane lists 21 pairs, linear only (observed 2026-11-28).
- The blob is ordered modifier-major. The `probe --raw` list of a Cluster plane (32 pairs) starts `XR30:...001 XB30:...001 ... Y210:...001`, then the same 14 formats under `...041`, then `...011`, and ends at `AR24:0x800000000000011` (observed 2026-11-28). So the 32 kept pairs are the 14 of `AFBC(16x16)`, the 14 of `AFBC(16x16|SPARSE)` and the first 4 of `AFBC(16x16|YTR)`. **94 of 126 pairs fall beyond index 32** (inferred arithmetic from the observed order): the other 10 pairs of `YTR` (XB24 to Y210) and all 14 pairs of each of the six modifiers `CBR`, `YTR|SPARSE`, `SPARSE|CBR`, `YTR|CBR`, `YTR|SPARSE|CBR` and `YTR|SPLIT|SPARSE`.
- Linear is **not** in the Cluster IN_FORMATS, so there is no "linear first" and no linear pair is hidden by the cap. This settles the point the design doc left open ("the probe prints in a different order or the Cluster planes list no linear pairs"): it is the latter (observed 2026-11-28). It matches the source: `format_modifiers_afbc` has no linear entry (read from source, [`rk3588-vop2-formats-source.md`](rk3588-vop2-formats-source.md)).
- The kernel nevertheless accepts linear on a Cluster plane. `kms_sweep modifiers --plane 45 --modifier linear`: ten formats (XR24 AR24 XB24 AB24 RG24 BG24 RG16 BG16 YUYV Y210) with the linear modifier gave `addfb=ok test_only=ok` although `listed=no`. XR30 and XB30 with linear gave `addfb=EINVAL`; YU08 and YU10 are `unsupported-format` at ADDFB (the tool cannot build those buffers). All 108 listed AFBC pairs that could be built passed TEST_ONLY (observed 2026-11-28, TEST_ONLY). The source agrees: `rockchip_vop2_mod_supported` returns true for LINEAR on RK3588 (read from source).
- The converse on an Esmart plane: `kms_sweep modifiers --plane 57 --modifier linear --modifier 0x0800000000000001`: the 19 buildable linear pairs passed; the 9 buildable AFBC pairs (not listed) got `addfb=ok` and `test_only=EINVAL` (observed 2026-11-28, TEST_ONLY). The list is enforced on Esmart.
- For a profile (inferred): a client that copies IN_FORMATS strictly cannot place a linear buffer on a Cluster plane, yet a linear buffer works. With the cap of 32 the profile keeps the plain `AFBC(16x16)` pair of every format and loses the variants.
- **Finding for composition-core, not changed here:** listing every Cluster pair needs `MAX_FORMATS` >= 126, or a representation as a format set times a modifier set. That is an owner decision.

## Q2. Which kernel does the target run?

**Answer: a mainline-based 6.18.55 kernel, not the vendor 6.1 kernel.**

- `uname -r` is `6.18.55-current-rockchip64` (Armbian "current" branch, built 2026-10-03), and the DRM driver reports `rockchip` 1.0.0 "RockChip Soc DRM" (observed 2026-11-28).
- The properties agree with the mainline driver, not the vendor one: only standard plane properties (no `SCALE_RATE`, no vendor window property), eight planes with one window each (observed 2026-11-28; see Q3 and Q8).
- Whether the Armbian tree differs from the pinned Linux v6.18 source behind the `read from source` tables (patches on top, the 6.18.55 stable delta) was not compared here. **Still open**, for the host item `kernel-source-compare`.

## Q3. How does a profile identify a window class?

**Answer: from the IN_FORMATS content (the modifier vendor). No property or name tells Cluster from Esmart.**

- No plane has a name property. The property set is identical on all eight planes: `CRTC_*`, `SRC_*`, `FB_ID`, `CRTC_ID`, `IN_FENCE_FD`, `IN_FORMATS`, `alpha`, `pixel blend mode`, `rotation`, `type`, `zpos` (observed 2026-11-28). There is no vendor property and no scaling property.
- `IN_FORMATS` separates the classes: Cluster lists only modifiers of vendor 0x08 (Arm AFBC), no linear, 14 formats; Esmart lists the linear modifier only, 21 formats including NV12, NV15, NV16, NV24 and NV30 (observed 2026-11-28). The rule "a listed modifier of vendor 0x08 means Cluster, otherwise Esmart" holds for all eight planes (inferred rule, observed data).
- `type`: Cluster0 (33) and Cluster1 (39) are Primary, the other six Overlay (observed 2026-11-28). `type` alone does not give the class. On the vendor 6.1 kernel the source note has Esmart windows as Primary candidates (read from source, design doc), so the rule must not depend on it.
- Object id order, ascending: 33 Cluster0, 39 Cluster1, 45 Cluster2, 51 Cluster3, 57 Esmart0, 63 Esmart1, 69 Esmart2, 75 Esmart3. The names come from the debugfs recording in [`observed/rk3588-topology.md`](observed/rk3588-topology.md) (observed 2026-11-28 there), the ids from this run. Ids may change between kernels and boots; the order is a weak hint only (inferred).
- `possible_crtcs`: plane 33 `0b01`, plane 39 `0b10`, the six others `0b11` (observed 2026-11-28). Not a class marker.
- Not usable as identity, because it is state: the `pixel blend mode` default is `None` on Esmart0 and Esmart1 and `Pre-multiplied` elsewhere, and the live `zpos` values are 0 1 2 3 0 1 6 7 in id order (observed 2026-11-28).
- `rotation` is a bitmask. `props` prints the current value only (1 = rotate-0 on all eight), so **the supported rotation and reflect bits are still open**. The source has Cluster with rotate 90/270 and reflect X/Y and Esmart with reflect Y only ([`rk3588-vop2-limits-source.md`](rk3588-vop2-limits-source.md); read from source).
- Scaling limits come from TEST_ONLY probing only ([`observed/rk3588-props.md`](observed/rk3588-props.md)).

## Q6. Is zpos global or per CRTC? What happens on equal zpos?

**Answer: partly open.** What was measured:

- Every plane has `zpos` `range 0..=7` and it is mutable (no immutable flag). The range is the same on the CRTC-0-only plane, the CRTC-1-only plane and the shared planes. It is a plane property, not a CRTC property, and its width equals the number of planes (observed 2026-11-28).
- Live values at dump time, ids 33 39 45 51 57 63 69 75: 0 1 2 3 0 1 6 7. Plane 33 (active on CRTC 81) and the inactive plane 57 both hold 0 (observed 2026-11-28).
- Distinct zpos on one CRTC: `kms_sweep combos --max 8 --sets 4` (TEST_ONLY, distinct ascending zpos, primary lowest). Every set of k = 1 to 4 planes was accepted (including 33,45,51,57 and 33,51,69,75). Every set of k >= 5 returned `EINVAL`, up to the full seven candidates (observed 2026-11-28, TEST_ONLY):

  The k = 5 refusal is not a zpos refusal (the sets use distinct values); the cause is not identified here. It belongs to the Q4 session, which sweeps up to 8 windows.
- **Equal zpos on two planes of one CRTC: still open.** `kms_sweep` always assigns distinct ascending values and has no option for equal ones, and this item may not change examples. Expectation, not verified in this session: the DRM core normalises zpos by sorting on zpos and then plane id, so a tie is resolved by plane id instead of failing (inferred; `drm_atomic_normalize_zpos` was not read against the 6.18 tree).
- **Same zpos on planes of different CRTCs: not testable on this board.** HDMIA-2 is disconnected, so CRTC 82 cannot be activated; only one CRTC was active (observed 2026-11-28). Whether zpos is global or per CRTC is therefore **still open**. The read-only data (one 0..=7 range on every plane, including the plane that reaches CRTC 82 only) neither shows nor excludes a per-CRTC normalisation.

## Q8. Do Cluster win1 or Esmart multi-area become planes?

**Answer: no, on this kernel.**

- The board exposes exactly eight planes: four Cluster and four Esmart, one window each (the debugfs names in the earlier recording all end in `-win0`), ids 33 to 75 at a stride of 6 (observed 2026-11-28). No extra plane exists for a second Cluster window or a second Esmart area: 8 planes, not 12.
- The source agrees: the mainline table has one window `win0` per Cluster and no `win1` entry, and Cluster line-buffer mode 1 (two sub-windows) is never written ([`rk3588-vop2-formats-source.md`](rk3588-vop2-formats-source.md), [`rk3588-vop2-limits-source.md`](rk3588-vop2-limits-source.md); read from source). `support-multi-area` is a vendor 6.1 device-tree option (read from source, design doc).
- So the Cluster main/sub pairing rule has no case on this board, and `MAX_PLANES = 16` is far from reached by 8 planes (inferred). A vendor 6.1 kernel was not tested.

## Findings for the planner

- **MAX_FORMATS (composition-core decision, unchanged):** a Cluster plane has 126 pairs; the cap keeps 32.
- **MAX_PLANES:** 8 planes here; no pressure.
- For `profile.rs` (later item `profile-tighten`): the class test "any modifier of vendor 0x08 in IN_FORMATS" is measurable today. No code was changed here.
- Tool gap: `kms_sweep` cannot request equal zpos or use a second CRTC, so Q6 stays open until a tool exists.
- Sets of five planes at 1920x1080 are refused (`EINVAL`) while four pass; the Q4 session should map that refusal.
