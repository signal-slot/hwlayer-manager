`docs/rk3588-vop2-zpos-source.md` §6 left open. Session procedure:

## Q1: raw IN_FORMATS, and what MAX_FORMATS = 32 hides

Observed 2026-11-28 (`probe --raw`, and the `IN_FORMATS` blob line per
plane):

- The four Cluster planes (ids 33, 39, 45, 51) each carry
  `IN_FORMATS (126)`: 14 formats × 9 Rockchip modifiers
  (`0x800000000000001`, `0x…011`, `0x…041`, `0x…051`, `0x…071`, `0x…081`,
  `0x…091`, `0x…0c1`, `0x…0d1`). 126 pairs, 94 more than the 32 the capped
  listing shows: the recorded truncation at 32 is the cap, not the kernel.
- The four Esmart planes (57, 63, 69, 75) each carry `IN_FORMATS (21)`:
  21 formats, all with the linear modifier `0x0` only.
- No Cluster plane lists a linear pair anywhere in its blob. The first pair
  as the kernel stores it is `XR30:0x800000000000001`; the listing follows
  blob order (the `0x…01` group, then `0x…41`, then `0x…11`). So the
  ordering question resolves: the probe does not reorder, and on a Cluster
  plane there is no linear pair to sort first.
- Linear buffers are nevertheless accepted on a Cluster plane (observed
  2026-11-28): `kms_sweep replace` committed a dumb (modifier 0) XRGB8888
  framebuffer on primary 33 (`SETUP commit=ok`), and the kernel's own state
  dump shows plane 33 long displaying framebuffer 90, `format=XR24`,
  `modifier=0x0`, allocated by `[fbcon]`.

Finding, not a change (the plan leaves caps to `composition-core`):
`MAX_FORMATS = 32` truncates a 126-pair Cluster advertisement to 32; raising
it is a core decision.

## Q2: which kernel

Observed 2026-11-28, five tool runs: `KERNEL 6.18.55-current-rockchip64`
(Armbian version string). This is the same board kernel already recorded in
`docs/rk3588-backend-design.md` §2 (observed 2026-11-27); the session repeats
the fact.

Host-side check the same day (`git ls-remote`, read-only): the tags pinned in
`docs/rk3588-vop2-zpos-source.md` are the canonical refs — mainline `v6.18`
points at commit `7d0a66e4bb9081d75c82ec4957c50034cb0ea449`, stable
`v6.18.55` is tag object `5c70e682251f50354711645fd494be38495f46ec`. The
board's version base is therefore the same release that pin names.

Behavior check (observed 2026-11-28): every source prediction the board could
test in this session held — equal zpos accepted, contiguous normalized ranks
(Q6), a fifth plane on one CRTC rejected `EINVAL` (Q4), `zpos 0..=7` on every
plane. Inferred: for the code paths the design table depends on, the board
kernel behaves like the pinned `v6.18.55` rows. The Armbian tree's own patch
list was not diffed: file downloads (clone/fetch) are refused on this worker,
so the vendor-6.1 half of Q2 stays open, and this answer covers only the
measured board.

## Q3: how a profile tells the window classes

Observed 2026-11-28:

- The two format families are distinct and stable across a class: Cluster
  planes list exactly the 9-modifier, 14-format set; Esmart planes list
  exactly the 21-format, linear-only set.
- No `SCALE_RATE`, `SCALING` or class-name property exists on any plane of
  this kernel (the props dump has none).
- `rotation` reads value 1 (rotate-0 only) on all eight planes, so rotation
  does not separate the classes on this kernel.

Answer (inferred from these observations): identify the class from the
`IN_FORMATS` family — a 9-modifier AFBC-style set means Cluster, a 21-format
linear-only set means Esmart. The debugfs names (`Cluster0-win0` …
`Esmart3-win0`) are a kernel dump, not KMS, so a KMS-only backend should not
depend on them.

## Q4: eight simultaneous windows

Observed 2026-11-28 (`kms_sweep combos`, DATE 2026-11-28T12:37:44Z, `--max 8`
on 7 candidate planes — the NOTE line says `--max 8 is more than the 7 usable
planes`):

- k = 1..4: every requested set accepted (37 sets, `result=ok`).
- k = 5: all 15 sets `result=EINVAL`; k = 6: all 6 sets `EINVAL`; k = 7: the
  one set `EINVAL`.
- `COMBO_MAX accepted_k=4`.

Answer (observed 2026-11-28): eight simultaneous windows on one output are
not achievable on this kernel; the largest accepted set is 4 planes, and it
does not grow with zpos choices. This matches the source limit
`nlayers = win_size / nvps = 8 / 2 = 4` per CRTC
(`docs/rk3588-vop2-zpos-source.md` §4, read from source): with only one
connected CRTC in use, 4 is also the board-wide maximum today.

## Q6: zpos — global-looking property, per-CRTC ordering, equal values

Source half: `docs/rk3588-vop2-zpos-source.md` (read from source). Board
half, observed 2026-11-28:

- `plane_commit` with `zpos=5` written on both planes 45 and 51 (equal
  values, plus primary 33 at 0): `TEST_ONLY ok` (DATE 2026-11-28T12:38:05Z)
  and a real commit `COMMIT ok` (DATE 2026-11-28T12:43:48Z) followed by
  `STATE plane=45 … zpos=5` / `STATE plane=51 … zpos=5`. Equal values are
  not a rejection.
- The kernel state dump after the session (read over debugfs at about
  13:05Z, holding the last committed state of crtc 81):
  `plane[33]: Cluster0-win0 … normalized-zpos=0`,
  `plane[45]: Cluster2-win0 … normalized-zpos=1`,
  `plane[51]: Cluster3-win0 … normalized-zpos=2` — the tie of zpos 5/5 broke
  by object id (45 below 51), and the ranks are contiguous 0..2, not the
  written values.
- Every plane offers `zpos` mutable `0..=7` on both CRTCs (observed 2026-11-28,
  props and probe lines), the same range everywhere — the property is
  global-looking; ordering stays per CRTC.

Untested on this board: the two-CRTC predictions (`docs/rk3588-vop2-zpos-source.md`
§6 items 4 and 7): crtc 82 has no connector, so it cannot hold planes.

## Q8: Cluster win1 and Esmart multi-area as planes

Observed 2026-11-28 (`probe --raw` plane list, and the debugfs state dump):
the kernel registers exactly 8 planes — `Cluster0-win0`, `Cluster1-win0`,
`Cluster2-win0`, `Cluster3-win0`, `Esmart0-win0` … `Esmart3-win0`. There is
no `win1` and no second-area plane. Answer: on this kernel the extra windows
do not become DRM planes, so the 8-plane board and the 4-per-CRTC split are
the whole story, and the pairing question does not arise.

## Q9: overlay flip behaviour and latch events

`twoplane` cannot run on this board (observed 2026-11-28, DATE
2026-11-28T12:39:04Z): `VERDICT twoplane: FAIL no primary plane with a linear
32-bit RGB format: driver rockchip mode 1920x1080@60.000Hz`. Root cause
(observed + read from source): the harness only starts on a *primary* plane
that lists a linear RGB pair (`lists_linear` in `twoplane.rs`), the Cluster
primaries list none (Q1), and dumb buffers are always linear — even though
the kernel accepts linear buffers on Cluster (Q1). That gate, not the kernel,
blocked the measurement.

New tool for it: `flip_probe`
([`flip_probe.rs`](../crates/composition-drm/examples/flip_probe.rs)) flips
only an overlay and needs no linear primary. It was built, unit-tested
(`cargo test -p composition-drm`) and run on the board.

Pending-commit behaviour, observed 2026-11-28 (`kms_sweep replace`, three
runs, all DATE 2026-11-28T12:42:47Z): `SETUP commit=ok events=1` and
`REPLACE first=ok second=EBUSY events=1` in all three runs. A flip that has
not yet latched cannot be replaced by a second flip; the accepted flip still
produced exactly one page-flip event. (The `EBUSY` is the DRM core refusing
a commit against a pending flip; read from source in
[`docs/drm-pending-commit-source.md`](drm-pending-commit-source.md) for the
core-side rule.)

Sustained counts, observed 2026-11-28 (`flip_probe --frames 120`, DATE
2026-11-28T13:03:39Z), overlay plane 45, two 640x360 dumb buffers centred on
the 1920x1080 output, `zpos=2`, never touching the primary, connector or mode:

```text
SETUP commit=ok events=1
FLIPS frames=120 committed=120 events=120 missed=0 late=10 errors=0 first_error=none drain=0 aborted=0
LATENCY samples=120 target_us=16666 min_us=16553 avg_us=18043 max_us=33541
RESTORE ok
VERDICT flip_probe: PASS
```

Reading (observed + inferred): the driver reports one page-flip event per
accepted flip (120/120, nothing merged or left over), and waiting each event
before the next commit produced zero rejections. Event latency clustered at
one refresh period (minimum 16.553 ms against a 16.666 ms period); 10 of 120
waits exceeded 1.5 periods and the worst was 33.541 ms, about two periods —
inferred: an occasional overlay flip latches one vsync later than its commit.

Not measured: a KVM picture of the flip (the camera/KVM device was not
available to this worker). `docs/rk3588-vop2-zpos-source.md` §7's visible-order
question stays open.

## Findings for composition-core (recorded, not changed)

- `MAX_FORMATS = 32` hides 94 of 126 Cluster pairs (Q1, observed 2026-11-28).
- `MAX_PLANES = 16` is not the limit here: this board has 8 planes (observed
  2026-11-28).
- The `twoplane` harness gate `lists_linear` cannot run on RK3588 primaries
  even though the kernel commits linear buffers on them (Q9, observed
  2026-11-28). `flip_probe` is the tool that measures overlay flips there.
